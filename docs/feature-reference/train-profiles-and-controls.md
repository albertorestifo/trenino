# Train profiles, bindings, calibration, and hardware control

Baseline: `188f35e4108733358730e92ebd98f1912af5173a`. Static source/test review only: the scenarios below were not exercised against a simulator or hardware during this review. This document describes the implemented domain, including incomplete or surprising behavior that a rewrite must consciously preserve or change. UI events, database migrations, MCP tools, and hardware internals have their own references.

## Persistent model and context API

All schemas below have integer database IDs and UTC `inserted_at`/`updated_at` timestamps. Ecto casts accept enum strings as well as atoms. Unknown attributes are ignored by individual changesets. Foreign-key constraints require actual referenced rows at persistence time; schema declarations alone do not enforce cross-profile ownership or hardware type compatibility. Context methods generally return `{:ok, record}` or `{:error, changeset}`, getters use `{:error, :not_found}`, lists return a list except `list_elements` returns `{:ok, list}`. Bang getters raise. See [Train context](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train.ex) and [context tests](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train_test.exs).

### Profiles and equivalent identifiers

| Table/schema | Writable fields, defaults, validation |
|---|---|
| `trains` / Train | `name` required string; optional `description`; nested `identifiers` association with `on_replace: :delete`, `identifiers_sort` and `identifiers_drop` form parameters |
| `train_identifiers` / TrainIdentifier | `identifier` required trimmed string; belongs_to train; exact identifier globally unique |
| `train_elements` / Element | `name` required; `type` required enum lever/button; `train_id` cast with FK; has_one lever_config and button_binding |

A new profile needs at least one retained identifier. Replacing/removing the last loaded persisted identifier fails. Duplicate nested identifiers (after trimming) produce `identifiers: must be unique within a train profile`; cross-profile duplicate uses DB uniqueness. An unchanged loaded/not-loaded identifier association is allowed on updates; an already loaded empty association is rejected. Name/description have no domain maximum or uniqueness validation. Identifier ordering has no semantic priority; `Train.identifier_values` sorts strings for presentation. Multiple unrelated route prefixes can map one profile; matching remains case-sensitive prefix matching and ambiguity is an error, as detailed in [simulator reference](simulator.md).

Context inventory: `list_trains(opts \ [])` sorts name, optional preloads; `get_train(id,opts)` optional preloads; `get_train_by_identifier` preloads identifiers and elements/lever config; `create_train`, `update_train`, `delete_train`. `list_elements(train_id)` sorts name and preloads lever_config/notches/input_binding/input/device and button_binding/input/device; `get_element(id,opts)`; `create_element(train_id,attrs)`; `delete_element`. There is **no generic update_element** function in this context. `create_element` seeds train_id but also casts attrs.train_id; callers should not assume supplied parent IDs cannot be overridden. No element-name uniqueness or schema guard that a button binding only attaches to a button element exists.

Deletion delegates to Repo and migration cascades. Tests establish profile->elements cascade, element->button binding cascade and hardware-input->button binding cascade. Broader migration behavior is recorded in the data reference; deletion does not itself publish a train change or reload every controller.

### Lever configuration and notches

| Schema/table | Contract |
|---|---|
| LeverConfig / `train_lever_configs` | `element_id` FK, unique (one config per element); required strings `min_endpoint`, `max_endpoint`, `value_endpoint`; optional strings `notch_count_endpoint`, `notch_index_endpoint`, both set together or both nil; optional enum `lever_type` discrete/continuous/hybrid; `inverted` boolean default false; nullable UTC `calibrated_at`; has_many notches and has_one input_binding |
| Notch / `train_lever_notches` | `lever_config_id` FK; required `index` integer and `type` gate/linear; unique `(lever_config_id,index)`; `description` nullable; optional float ranges/values described below |
| LeverInputBinding / `lever_input_bindings` | Required `lever_config_id`, `input_id` with FKs; unique lever_config_id; `enabled` boolean default true |

Notch has **three distinct coordinate systems**. `input_min/input_max` represent normalized calibrated **hardware travel**, 0..1. `sim_input_min/sim_input_max` represent the **simulator InputValue to send**, with no 0..1 restriction (negative allowed). `value` (gate) and `min_value/max_value` (linear) represent observed simulator **output**, for description rather than runtime mapping.

A gate requires `value`. A linear requires min_value and max_value, but there is no validation that output minimum <= output maximum; unused output fields are not cleared automatically when type changes. Hardware range values must both be set or both nil, each within 0..1, min <= max. Simulator range pair must both be set or both nil and min <= max. Equal bounds are allowed for both pairs/types. Every changed float field is rounded to **two decimal places before validation**. Thus .125 persists as .13 and a narrow range may collapse; samples gathered at full ADC precision do not preserve that precision in persisted notches. Index is required but not validated nonnegative. Description/endpoint lengths and endpoint existence are not checked. A config can therefore be valid but operationally unmapped.

Context inventory:

| Operation | Behavior |
|---|---|
| `get_lever_config(element_id)` | Lookup by **element ID**, return config with notches |
| `create_lever_config(element_id,attrs)` / `update_lever_config(config,attrs)` | Changeset insert/update; no implicit analysis/calibration |
| `create_lever_config_with_analysis` | Transaction: put analyzer lever_type, create config, insert suggested notches; rollback errors |
| `update_lever_config_with_analysis` | Transaction: update config, delete old notches, insert new; **old hardware ranges are discarded** |
| Analyzer suggestion conversion | Copy suggestion `input_min/max` to persisted `sim_input_min/max`, copy type/index/output/description, leave hardware input ranges nil |
| `save_calibration(config,notches)` | Transaction replace all notches; convert keys to strings; assign indices by list order (ignores supplied index); set calibrated_at now |
| `save_notches(config,notches)` | Transaction replace all, assign indices by list order; preserve calibrated_at |
| `create_notch`, `update_notch`, `update_notch_description`, `delete_notch` | Direct row operations; no automatic gap repair/reindex/runtime reload |
| `update_notch_input_ranges(config_id, updates, inverted: bool)` | Transaction update rows by supplied ID, optionally set inverted, return reloaded config |
| `auto_distribute_input_ranges(config_id)` | Equal-width ranges `step=1/count`; persisted bounds use each **stored index** times step; zero notches is success unchanged |
| `validate_notch_ranges(config_id)` | Sort populated hardware intervals; detect missing coverage of [0,1], tolerating gaps <= .001; return `:ok` or `{:error,:gaps_detected,[{min,max},...]}` |

Important edge cases: `update_notch_input_ranges` does not verify each supplied notch belongs to the given config. Equal distribution assumes consecutive zero-based indices, and raises via `Repo.update!` if bad bounds result. Missing config handling is inconsistent: `get_lever_config` takes element ID, but both equal-distribution and validation pass their parameter named lever_config_id directly to it, and equal-distribution reload again uses a config ID. It works accidentally when IDs coincide; callers cannot rely on correctness when they diverge. Gap validation allows overlaps and ignores notches without ranges; it is not a complete structural validator. No mapping save automatically guarantees full coverage. Reanalysis/replacement assigns new row IDs.

### Train input destinations versus virtual joystick

`bind_input(config_id,input_id)` upserts one lever binding. `get_binding(config_id)` preloads input; `unbind_input(config_id)` returns :ok or not_found; `set_binding_enabled(config_id,bool,opts)` updates it. `list_bindings_for_train(train_id)` joins config/element and preloads input, lever config/element/notches; disabled rows remain in the list and controllers filter them.

Lever and button create/update/enable share `save_binding`: an SQLite **immediate transaction** obtains writer lock before inspecting the input's destinations. Invalid changeset rolls back first. An enabled train binding conflicts with an existing `VirtualJoystick.Mapping` for its input: default `{:error,:destination_conflict}` leaves both persisted states unchanged. With `replace?: true`, delete the mapping and insert/update binding atomically. Disabled bindings do not remove/conflict with vJoy mappings until enabled. If replacement occurred, cast reload to the corresponding running train controller and vJoy Manager. Ordinary binding persistence without replacement does **not** automatically reload the runtime controller; callers must do so. The lookup `lock_input` is not an SQL row lock; transaction mode is the synchronization mechanism.

Same hardware input can be persisted for multiple train bindings, including multiple elements on the same train; no unique input constraint prevents it. Runtime lever/button lookup is `Map.new` keyed by input_id: in a single controller the last enumerated enabled binding wins, so this persistence allowance does **not** implement reliable one-to-many fanout. LeverController and ButtonController have separate maps and no mutual arbitration. Neither schema changeset checks input type/calibration; UI/MCP selection paths may enforce more restrictions.

Evidence: [Train context](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train.ex), [button schema constraints tests](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train/button_input_binding_test.exs), [vJoy replacement context tests](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train_test.exs), [controller replacement test](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train/button_controller_test.exs). See virtual joystick reference for the reverse-direction conflict policy.

## Lever movement and write scheduling

`LeverMapper.map_input(config,float)` accepts **float** normalized input in [0,1], otherwise out-of-range floats return no_notch; nonfloat input has no matching public clause. If config.inverted is truthy, effective input becomes round(1-input,2). Find the first supplied notch with nonnil hardware bounds satisfying min <= effective < max. If none, permit exact upper boundary only when max == 1.0. Gaps return no_notch. Overlaps resolve by supplied list order rather than specificity/index; the mapper does not sort. A zero-width gate below 1.0 never matches this rule. A zero-width last notch at 1.0 can match the exceptional boundary.

Gate mapping returns round((sim_min+sim_max)/2,2). Linear mapping computes `p=(effective-input_min)/(input_max-input_min)` and returns round(sim_min+p*(sim_max-sim_min),2). For `inverted == true` and a reversed layout, use `1-p` within linear notches. Reversed layout detection needs >=2 fully mapped notches: compare notch with lowest input_min and notch with highest input_max; reversed if first.sim_input_min > last.sim_input_max. It does not infer direction from output value. Missing sim bounds return no_sim_input_range; direct `calculate_sim_input` calls with missing hardware bounds return unmapped_notch. `calculate_value` is a legacy alias to the modern simulator-input mapping. Equal linear hardware bounds pass the schema but direct mapping at an eligible boundary can divide by zero.

Example: gate observed output -11 at hardware 0..05, simulator input .00..04 -> sends **.02**, never -11. Linear hardware .05..45 -> sim .05..44 at hardware .25 gives approximately .25 after rounding. Both negative and >1 simulator inputs are possible because only hardware normalization is bounded.

`LeverController` is a named GenServer. On init subscribes Train detection, simulator connection and serial device updates; rebuilds input lookup from connected serial devices whose device_config_id resolves to saved Hardware.Device, subscribes each new port's input events, and loads active profile if any. Input lookup maps `{port,pin}` to input_id/type/calibration. Rebuilding drops stale entries but does not unsubscribe old port topics. Bindings load from enabled train rows into input_id map. Calibration changes need lookup rebuild or an appropriate device event; loading bindings alone does not recalculate calibration lookup.

On `{:input_value_updated,port,pin,raw}`: require active profile, known input, enabled binding, calibration with positive total travel. `Calculator.normalize(raw, calibration)` produces calibrated integer travel (handles inversion, rollover, dead zone in hardware subsystem); divide by total_travel and round to two decimals; map through LeverMapper. Any lookup/normalization/mapping error is silently skipped. It does not require input_type analog at this runtime layer.

Simulator writes run under `Trenino.TaskSupervisor`, with at most one in-flight task **per lever config ID**. Pending tuple `{config, latest_value, task_or_nil}` is updated with newer samples while task runs: intermediate jitter samples are dropped. On success if latest equals written, remove pending; if changed, immediately start latest. Independent levers can write concurrently. No global duplicate-value cache suppresses identical new inputs after the previous write finished. No takeover/pickup logic waits for physical position to match game position.

On error or writer DOWN retain latest with task nil and schedule bounded retries at **200,400,800 ms** (initial plus up to 3 retries). Fresh input during a scheduled retry replaces value without bypassing delay. Once budget exhausted, retain latest until new input/reconnect can restart; new input when no timer/task clears budget. Global disconnect cancels retry timers but retains targets and any in-flight writers; it does not cancel the HTTP task. Connected event clears retry budget and starts retained idle writes. Train change/deactivation/reload brutally stops outstanding writers and cancels timers, preventing stale delivery to another profile. An HTTP request already applied in the simulator cannot be undone by killing the task.

## Two simulator calibration approaches

### Empirical analyzer

The modern `LeverAnalyzer` sweeps and observes **output plus actual input plus notch index**, groups/merges zones, and creates `sim_input_min/max` through Train analysis helpers. See [full algorithm](simulator.md#empirical-lever-analysis-leveranalyzer). This mutates game state during configuration. Newly analyzed notches still need hardware ranges.

### Legacy `LeverSession`

This is a separate named, temporary GenServer keyed by config ID in Trenino.Registry. `SessionSupervisor` is a one_for_one DynamicSupervisor, supports independent lever sessions and notch-mapping sessions, checks duplicate sessions **by type and config**, permits different levers concurrently; it does not prevent a legacy calibration and mapping session for the same config from coexisting. Start duplicate -> already_running; stop nonexistent -> not_found; race where child ends during terminate is treated as success. LeverSession self-starts via initialize; completion/error stops and is not restarted.

Initialization reads configured min/max and notch count. Exactly one notch skips sweep and saves one linear output range spanning min/max (calibration_skipped true). Otherwise set min, read initial notch index, and sweep using absolute **.025 input increment**, not normalized percentage, with 5 ms delay between steps; no extra settling delay between set and reads within a step. Stop before next value >= max-.001, finalize through max. For same notch index, compare set vs read InputValue: absolute difference >= .001 marks gate and captures read value; gate classification takes precedence over later linear observations. A changed index finalizes previous notch at the next setpoint, resets classification; the transition sample itself does not classify the new notch. Default unclassified -> gate using start value. Samples/values are rounded to two decimals when saving.

Progress topic `train:calibration:<config_id>` emits `{:calibration_progress,%{lever_config_id,step,progress,current_value,notch_count}}`; result is `{:calibration_result,{:ok,config}|{:error,reason}}`. Internal steps initializing/calibrating/saving/complete/error; progress ratio uses min/max span. `get_state(config_id)` returns live internal state or nil. Source errors stop with shutdown reason; explicit cancellation via supervisor terminates without dedicated canceled result. No restore of previous simulator position occurs.

**Compatibility gap:** LeverSession only saves type/output/description fields to `Train.save_calibration`; it does **not** save either simulator-input ranges or hardware-input ranges. Existing notches are replaced, so running it over a modern analyzed configuration destroys those ranges. It also calls configured notch endpoints even though LeverConfig permits both nil (Client.get_int guards binary path). A “calibrated_at” timestamp therefore does not imply a lever is ready for modern LeverMapper.

Sources: [LeverSession](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train/calibration/lever_session.ex), [session supervisor](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train/calibration/session_supervisor.ex), [tests](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train/calibration/lever_session_test.exs) exercise single linear skip, gates, linears, progress, errors, duplicates, lookup and state with mocked Client. The module prose still says .01 steps; constant is .025.

## Guided physical notch mapping

`NotchMappingSession` is a GenServer registered by config ID. Required start opts: preloaded lever_config/notches, port, pin and Hardware.Input.Calibration. It subscribes Hardware input values for the port, gets Calculator.total_travel, sorts notches by index and builds public notch metadata including sim ranges; initializes one nil capture per notch. There is no startup guard for zero notches or invalid/zero total travel. It does not monitor a UI owner or implement a session inactivity timeout. Because restart is not marked temporary, its default GenServer child restart behavior differs from LeverSession.

Normal states: ready -> `{mapping_notch,0}` -> each next notch -> preview -> saving -> complete. Begin mapping only in ready. Per notch, initial positioning updates current_value without collecting samples. `start_capturing` resets samples/extrema, enables capture, emits capture_started. Incoming **matching pin** readings normalize to full-precision calibrated integers; while capturing track all samples/current_min/current_max. The callback ignores message port (`_port`), trusting subscription scope; explicitly delivered wrong-port same-pin messages would be accepted. It has no catch-all arbitrary-message handler.

`capture_range` requires at least **one** sample and nonnil extrema; accepts min==max for any notch, including linear. It stores range and advances, stops capture and clears samples. No requirement for the ten-sample “is_stable” flag, minimum width, monotonic sequence, contiguous coverage or nonoverlap is enforced. Gates and linears have the same capture validation. Repeated capture, re-navigation, or different notch orientation is allowed. `stop_capturing` and `reset_samples` both discard current samples/extrema and stop capture, leaving stored ranges. `go_to_notch(index)` works from any state if 0 <= index < notch count, resets capture; invalid index error. `go_to_preview` requires every capture nonnil; `save_mapping` only in preview. Aliases `capture_boundary` / `go_to_boundary` remain for compatibility.

Before saving, compare hardware-center extremes with simulator-center extremes among valid paired notches; need >=2 pairs. If low hardware corresponds to higher simulator center, auto-detect inverted true. Normalize ranges by total_travel (round four decimals); when inverted, persist `[1-norm_max,1-norm_min]`. Notch changeset rounds again to **two** decimals. Zero travel fallback writes both bounds 0. Save ranges and inverted flag in one Train context transaction; emits complete/result success or error. Complete process remains alive until explicitly canceled/stopped; save error also ends at complete. A successful mapping does not set calibrated_at, fill gaps, or itself reload LeverController.

Topic `train:notch_mapping:<id>` emits session_started, step_changed, sample_updated, capture_started, capture_stopped as `{event, public_state}`, and `{:mapping_result,{:ok,config}|{:error,reason}}`. Public state has lever_config_id, notch_count, notches, total_travel, current_step/current_notch_index/current_notch, is_capturing, captured_ranges, current_value/min/max, sample_count, can_capture, all_captured, result; legacy boundary_count=count+1, current_boundary_index, captured_boundaries, notch_descriptions, is_stable (sample_count>=10). Cancel casts normal stop and does not broadcast a canceled result.

Sources: [mapping session](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train/calibration/notch_mapping_session.ex), [tests](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train/calibration/notch_mapping_session_test.exs). Tests cover state, one-point gate capture, immediate can_capture, calibrated range tracking, pin filtering, capture progression, reset/navigation, incomplete-preview rejection, save/public events and cancel. They use injected hardware messages and SQLite; they do not validate gaps or exercise auto inversion in the mapped-save scenarios.

## Button binding contract and runtime

ButtonInputBinding / `button_input_bindings` fields: required `element_id`, `input_id` (FKs), one binding per element, `enabled=true`, `on_value=1.0`, `off_value=0.0` (changed floats rounded two decimals), `mode=simple` (simple/momentary/sequence/keystroke), `hardware_type=momentary` (momentary/latching), `repeat_interval_ms=100`, nullable endpoint, keystroke, on_sequence_id, off_sequence_id (sequence FKs).

Validation: simple requires endpoint; momentary requires endpoint and repeat_interval_ms; interval, whenever present, must >0 and <=5000 even in other modes. Sequence mode needs at least one sequence; off sequence only valid for latching hardware in sequence mode. Keystroke requires a string but schema does not validate key syntax or executable availability. On sequence may remain populated outside sequence mode; off sequence must be cleared to change away from sequence. No same-train check for referenced sequences; no input-type check. Only element and input are universally required, so on/off can be explicitly nil at schema level (defaults apply when omitted).

Context methods `get_button_binding(element_id)` preloads input/device; `create_button_binding(element_id,input_id,attrs,opts)` merges IDs with matching atom/string key style; update/delete/enable (delete by element ID returns :ok); `list_button_bindings_for_train` returns disabled and enabled rows with element/input/device; `list_button_elements` filters type button and sorts name. Shared destination-conflict transaction described above applies.

`ButtonController` subscribes train detection and serial events, loads active profile, rebuilds connected hardware input lookup. It requests `include_virtual_buttons: true`, filters input_type button, so physical and matrix virtual buttons use the same event path. `{port,pin}->input_id`, then input_id->enabled binding; accepts **raw integer 1 or 0 only**, all else skip. No calibration is required. hardware_type does not itself convert momentary presses into toggle state; latching hardware supplies stable high/low transitions.

| Mode | Press=1 | Release=0 |
|---|---|---|
| simple | If last_sent != on_value, synchronous Client.set, cache on, publish pressed | If last_sent != off_value, synchronous set, cache off, publish released |
| momentary | Derive `.Interacting`, write 1 first then InputValue on; store active, queue immediate repeat | Remove active/cancel loop; write InputValue off first then Interacting 0 |
| sequence | Spawn ordered on-sequence worker, track PID; nil/empty sequence skips | Cancel tracked worker for **both** hardware types; latching may spawn off-sequence; momentary only broadcasts released |
| keystroke | `Keyboard.key_down(string)`; publish/cache only on success | `Keyboard.key_up(string)`; publish/cache only on success |

Momentary repeats `send(self(), {:momentary_repeat,element_id})` immediately after each synchronous HTTP set. **repeat_interval_ms is stored/validated/logged but ignored at runtime**; latency/mailbox determine rate. Every duplicate press queues another repeat chain; no dedup guard prevents that. Release removes active entry so stale repeat messages cease. Endpoint derivation replaces `.InputValue` with `.Interacting`; otherwise replaces last dotted suffix, and if no suffix exists may leave unchanged. Return/error results from press/release writes are not used to gate cache/events, and errors are mostly silent; no button retry/retained-write queue exists. A lost simple-mode write can be cached as delivered and repeated identical hardware state suppressed.

Button state event topic `train:button_values`: `{:button_state_changed,element_id,%{value: value_sent,pressed: boolean}}`. These express requested action/local state, not simulator acknowledgment. Sequence broadcasts use binding on/off values for UI state; those values are not extra simulator commands in sequence mode. Keystroke mode can operate without simulator connectivity, but still needs an active profile and matching hardware. Keyboard is an external executable wrapping Windows SendInput; resolution checks APP_PATH sidecar, priv/bin, then development release/debug binary. Utility errors return keystroke_not_found/command_failed. No focus selection occurs at this layer.

Train change/deactivation or reload cancels tracked sequence workers and momentary repeats, clears caches/bindings as appropriate, but **does not send momentary off/Interacting=0, release held keystrokes, or compensate partially executed sequences**. Keystrokes are never put in active_buttons, so cancel_all cannot release them. Serial device disconnect only rebuilds lookup and does not cancel active button state; a release event may never arrive. ButtonController does not subscribe to simulator status; set helper reads current status per action.

## Output bindings (LED conditions)

OutputBinding / `train_output_bindings`: required train_id, name, output_id, endpoint, operator; output_type enum **led only**, default led; enabled true; nullable numeric value_a/value_b, rounded two decimals. Numeric operators gt/gte/lt/lte/between require value_a; between additionally requires value_b. eq_true/eq_false require no numeric threshold. FKs train/output; one binding per `(train_id,output_id)`; one output may be reused in different profiles. No ordering check value_a<=value_b, name length, hysteresis, debounce, inversion flag, or endpoint type validation. Context lists by name with output/device, enabled list for runtime, get/create/update/delete.

OutputController subscribes **train detection only**. On activation/reload, clean old subscriptions, set previous outputs low, load enabled rows, group by endpoint and subscribe at 1000+index. Only successful subscribe groups are stored, each current_state=false. Every 200 ms after poll completion, read each subscription, require first entry NodeValid true and nonempty Values; take first value, round numeric to two decimals, preserve booleans. Invalid nodes/malformed/failed reads retain prior hardware/logical state. Evaluate gt/gte/lt/lte; between inclusive; boolean equality only accepts actual booleans (1/0 are not truthy conversions). Type mismatch returns false. **There is no hysteresis**: values toggling across threshold can cause switching each poll.

Write only when condition differs from cached current_state: resolve saved output.device.config_id to live serial port, send pin high/low via Hardware.set_output. No port -> skip, failed write -> ignored; **cache still changes**. Initial false is not proactively transmitted for newly loaded outputs. Unlike DisplayController, hardware reconnect does not invalidate current_state/replay stable values. Polling while simulator disconnected keeps state and reschedules if bindings exist; it does not turn outputs off until deactivation/cleanup. If loaded while disconnected bindings/subscriptions are empty, and because controller does not subscribe to simulator status, reconnect alone does not rebuild. If game loses subscription IDs, no automatic resubscription occurs; reload/profile change is needed.

Source [OutputController](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train/output_controller.ex), [schema](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train/output_binding.ex), [schema tests](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train/output_binding_test.exs), [context tests](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train/output_binding_context_test.exs). **Test limitation:** [output_controller_test.exs](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train/output_controller_test.exs) labels itself integration but recreates private evaluate_condition in a local helper and largely tests context rows. It does not start the production GenServer or prove subscription/hardware lifecycle behavior; this review derives that behavior from source.

## Display bindings (I2C text)

DisplayBinding / `train_display_bindings`: required train_id, i2c_module_id, endpoint, format_string; optional name <=100 chars; format_string default `{value}`, length 1..200; enabled true; FKs train/module, unique `(train_id,i2c_module_id)`. Nullable integer script_id exists but is **reserved, not cast, not associated or used**; Lua-based display handling is separate. Context list/get preloads module/device, lists sorted name, enabled list sorted name, create/update/delete. `list_all_i2c_modules` delegates hardware for selection.

Format tokens `{value}` -> to_string(value), `{value:.Nf}` -> numeric formatting with N=0..10, nonnumeric fallback to_string. Literal prefixes/suffixes and multiple tokens work; format with no tokens is literal. Validation removes recognized tokens then rejects any remaining `{value` substring; it does not parse arbitrary braces as an expression language. Unsupported precision/type/incomplete value token produces error `Use {value} or {value:.Nf}, with precision from 0 to 10`. Runtime rendering of legacy numeric precision outside 0..10 safely falls back to raw string. No unit conversion/expression evaluation occurs. For m/s to km/h use a script.

DisplayController subscribes train, simulator connection, serial device updates and configuration_applied. Activation/reload cleans old subscriptions and blanks previous display, loads enabled rows, groups by endpoint at 3000+index. Every 200 ms poll first entry NodeValid true/nonempty Values, take first value, round numeric two decimals, clamp to configured **HT16K33 minimum if numeric and below minimum**, format text. If text equals last successfully delivered text, skip. On first/newly invalidated delivery, send module brightness then encoded segments (HT16K33 only). Cache text **only on success**; failed brightness/segments/no-port retries on later poll even if unchanged. Device update invalidates all last_text to nil, replaying brightness/text on reconnect.

Simulator connected event with active train cleans and rebuilds subscriptions, including rows loaded while disconnected. Other simulator statuses are ignored; stale text can remain until train deactivation. Configuration applied reloads persisted module address, encoding, brightness/minimum and bindings; skips blanking **old addresses** after deployment. Removed modules vanish through persisted bindings/cascades. Deactivation blanks enabled loaded displays and unsubscribes if game currently connected; no automatic module shutdown beyond blank text. Poll scheduler cancels previous timer before replacing it, limiting duplicate live timers. Display text length/glyph selection/alignment is delegated to hardware chip encoding.

Sources: [binding](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train/display_binding.ex), [formatter](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train/display_formatter.ex), [controller](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/lib/trenino/train/display_controller.ex), [formatter tests](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train/display_formatter_test.exs), [controller tests](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/test/trenino/train/display_controller_test.exs). Tests use mocked serial/Client and verify retry uncached failures, no-port behavior, hardware reconnect text/brightness, game reconnect subscription rebuild, persisted settings replay, removed modules, nil minimum and poll timer cancellation.

## Rewrite decisions exposed by this implementation

| Area | Current boundary/limitation to decide explicitly |
|---|---|
| Local configuration updates | Context CRUD usually does not notify runtime; UI/MCP must sync/reload appropriate controller |
| Binding fanout | Multiple persisted same-input bindings collapse in map-based runtime lookup |
| Input calibration | Hardware calibration and per-profile notch mapping are separate; ready timestamp is not sufficient |
| Numeric precision | Hardware normalize-to-float, persisted notches and writes round to .01; display input similarly rounded before formatting |
| Range quality | Schema accepts equal bounds; context coverage checker ignores overlap and is subject to config/element ID confusion |
| Automatic refresh | Lever retains/retries targets; Display resubscribes/replays; Output/Button/Script have different reconnect handling |
| Competing writers | Script output/display actions can target same hardware as bindings; no arbitration/priorities |
| Shutdown/reset | Button cleanup does not guarantee simulator off/key-up; output cleanup low; display cleanup blank; script cleanup no output reset |
| Historical architecture guide | [lever_input_mapping_architecture.md](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/docs/lever_input_mapping_architecture.md) maps output value/min/max directly and calls wizard proposed; current runtime requires sim_input_min/max and wizard exists |
| Historical train guide | [train-configuration.md](https://github.com/albertorestifo/trenino/blob/188f35e4108733358730e92ebd98f1912af5173a/docs/train-configuration.md) says full coverage/no overlap validation and fixed momentary interval; current backend does not enforce either claim |
