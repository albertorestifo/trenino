# vJoy configurator implementation and review repair (2026-10-25)

## Implemented behavior

- `vjoy::configurator` uses injected filesystem, clock, status, process and marker boundaries. Create/delete operate only on explicit selected IDs 1..16. Create arguments are `ID -a x y z rx ry rz sl0 sl1 -b 32 -p 0`; delete arguments are `-d ID`. UAC cancellation 1223 has its own error. Polling is every 100 ms. The 10-second helper/confirmation deadline begins after UAC acceptance; preflight status/resource validation also has a bounded deadline.
- A pending creation marker is written in HKCU before elevation. The final per-device ownership marker is written only after a compatible descriptor is confirmed; ID 1 retains `VJoyDevice1CreatedByTrenino`. If the final marker write fails, the pending marker remains as recoverable provenance. Retry can promote a confirmed compatible pending device without launching the helper again. A compatible device with neither marker is foreign and cannot be adopted or deleted. Timeout/nonzero helper outcomes are reconciled with a fresh bounded status check before clearing or promoting markers; incomplete process cleanup blocks another mutation.
- `trusted_resource` validates from filesystem root through the independently derived executable directory, every resource path component, and each fixed helper. Windows `symlink_metadata` and the reparse attribute reject symlinks/junctions above or below the install directory. `vJoyConfig.exe`, adjacent `vJoyInstall.dll`, and `vJoyInterface.dll` must all be trusted regular files. No PATH/CWD or external-driver-directory fallback exists.
- The Windows configurator status path uses a same-executable `--internal-vjoy-status <ID>` worker dispatched before Tauri initialization. The parent starts it by absolute current-exe path, waits under the supplied budget, kills and reaps on timeout, and retains uncertain children. The worker validates installed DLL trust and uses the vendored vJoy SDK for status/descriptor classification. The desktop composition agent wired `status_worker_entry()` in `main` and passes `resource_dir().join("resources")` into `with_resource_dir`.
- Elevated `vJoyConfig.exe` runs through `ShellExecuteExW runas` with fixed args. The returned process is assigned to a kill-on-close Windows JobObject. Timeout terminates the job and waits for the process plus job accounting to reach zero. Assignment/termination/reap failures return `CleanupIncomplete`, retain handles, and prevent further configuration. `release_runtime()` also calls `settle_configurator()` and surfaces incomplete cleanup before shutdown acknowledgement.
- Manager `enable/retry/repair` set up missing selected devices, while startup avoids UAC. Free unmarked devices conflict on enable/retry; a pending marker can recover a prior creation. `disable()` releases local acquisition, rejects a lost ownership marker, deletes only selected owned devices, and persists off only after successful cleanup. `remove_leftover()` handles selected owned or pending leftovers, never foreign/busy/unselected IDs. The prior live dispatch, bounded recovery and non-deleting shutdown preference remain intact.

## Public interfaces

- `WindowsVjoyAdapter::with_resource_dir(PathBuf)` expects `<current_exe_dir>/resources` and independently anchors to `current_exe`'s directory. `WindowsVjoyAdapter::new()` derives that same installed path.
- `trenino_runtime::vjoy::windows::status_worker_entry() -> Option<i32>` must run before Tauri setup/single-instance hooks; desktop wiring is present.
- `VjoyManager::{enable, retry, repair, disable, remove_leftover, release_runtime}` provide lifecycle actions. `VjoyAdapter` now has default `can_configure`, `ownership_marker`, `creation_pending_marker`, `configure_create`, `configure_delete`, and `settle_configurator` methods, retaining compatibility with other adapters.
- `VjoyError::Configurator(ConfiguratorError)` includes typed `ForeignDevice`, `UacCancelled`, `Timeout`, `MarkerWriteFailed`, and `CleanupIncomplete` diagnostics. Desktop error mapping was handled by the composition agent.

## Round 2 review repair (supersedes pending-marker and direct-helper statements above)

- The pending marker now records **intent only**. It never authorizes adoption, acquisition, cleanup, or deletion of a compatible device. A separate durable confirmed marker is written only after the helper exits successfully and the expected compatible state is observed, before the final ownership marker. Marker-write failure can recover through this confirmed stage. Failed launch, timeout, stale pre-launch intent, and uncertain outcome cannot promote a foreign compatible device. Missing stale intent can be cleared safely. Manager startup/enable/cleanup now consult the confirmed marker for recovery and reject unconfirmed free devices.
- `ShellExecuteExW runas` now launches the installed same-executable broker, not the helper. The parent creates a random named kill-on-close job before launch. The elevated broker waits until `IsProcessInJob` confirms its own membership in that exact parent job. Only then does it validate the fixed installed resource trio, create `vJoyConfig.exe` **suspended**, assign it to a broker-owned kill-on-close job, and resume its primary thread. The helper and its descendants inherit the parent job, while the broker job also kills its helper tree if the broker exits unexpectedly. The broker waits for helper exit and job accounting to drain; the parent waits for broker exit and parent-job accounting to drain. Assignment, termination and reap failures fail closed. The early `status_worker_entry()` also dispatches this broker mode before Tauri. Main dispatch is guarded by `cfg(all(windows, feature = "rust-ui"))` so the legacy desktop feature still builds.
- Windows `driver_available()` and `device_status()` now use bounded same-executable worker probes, including manager startup/enable/cleanup preflight. The worker calls distinct raw native methods to prevent recursive child spawning. The manager no longer loads the SDK in these preflight methods; descriptor/acquisition and live reporting remain in-process per the retained architecture. Every status worker has a 10-second bound, kill/reap behavior, and retained incomplete cleanup.
- An ownership or confirmed-marker read error on a later selected ID now rolls back already-acquired IDs. If neutralization during rollback fails, that cleanup error is returned instead of being silently hidden. The fake adapter injects marker-read failure for the regression.
