## Remaining findings

1. **Critical — an uncertain HIGH write still disappears from lease cleanup.** `crates/trenino-runtime/src/composition/hardware.rs:73-88` waits for `send_message` success before adding the LOW target to `pending`. An error is not proof that the output was never energized: the real transport writes all frame bytes before flushing (`hardware/mod.rs:249-253`), and its caller may time out awaiting the reply (`hardware/mod.rs:531-533`) after dispatch. Reproduce: fake serial records/applies HIGH and then returns an acknowledgment error; delete that output row; call `suspend`. It returns success with an empty cleanup set and never sends LOW. This is the original stale-physical-target failure through a failed acknowledgment rather than a successful one. Track the conservative neutralization target before dispatch, retain it on all uncertain failures, and remove it only after acknowledged LOW/blank. Apply the same policy to nonblank display writes.

   **Executed regression:** `/tmp/trenino-composition-review-probe.rs`, `uncertain_high_is_not_forgotten_after_row_deletion`, compiled against the freshly built actual runtime, **failed**: actual reports `[SetOutput { pin: 4, high: true }]`; expected HIGH followed by LOW. The harness is a copy of `tests/effect_ownership.rs` with the fake appending its physical report before returning its injected error and the test failing the initial HIGH acknowledgment. This uses disposable SQLite and fake serial only. Existing `cargo test -p trenino-runtime --no-default-features --test effect_ownership --quiet` passed **2/2**, demonstrating the coverage gap.

2. **Important — Windows can spawn an escaping descendant before Job Object assignment.** `crates/trenino-runtime/src/keyboard/process.rs:28-29` calls ordinary `Command::spawn()` first; only afterward does `ProcessGroup::new` create/configure a job and call `AssignProcessToJobObject` (`:169-191`). The child can run and create descendants during that window. Those already-created descendants are not retroactively assigned when the parent joins the job; `TerminateJobObject`/kill-on-close then leaves them alive after a reported completed/expired action. The added comment and implementation handoff claim descendants are terminated. [Microsoft's job object contract](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) attaches subsequently created children after the parent is associated; it does not retroactively collect a process tree. **Targeted Windows test:** pause the parent between spawn and assignment, have a harmless helper immediately create a delayed sentinel writer, resume assignment and let the helper exit/timeout; verify the sentinel never executes. Create the child suspended, assign before resuming, or use atomic job assignment during process creation. This was established by source/API review; no native Windows execution is claimed.
