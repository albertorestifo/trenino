## Production behavior now connected

- Added `crates/trenino-runtime/src/composition/{mod,io,storage,keyboard}.rs`. `ControlRuntime` owns a dedicated Tokio host, TrainService, output/display controllers, ScriptRunner, SimulatorConnectionOwner, shared routing service and keyboard ownership. Uses the exact hardware resolver/resource arbiter handles supplied by desktop; no second routing authority or AppServices ownership cycle.
- Database sources load actual enabled scripts/output/display bindings and resolve hardware device config IDs and HT16K33 parameters. Failed reads emit diagnostics and fail closed to empty actuation. Script output/display effects go through actual serial hardware dispatch; unknown/disconnected devices emit diagnostics.
- Sync simulator ports use a dedicated IO thread/reactor with 64 request slots and 3-second enqueue-to-completion deadlines. Queued requests expire before execution; in-flight futures cancel at deadline or IO shutdown. No nested Tokio Handle.block_on. Output/display sync controllers now run on separate blocking hosts, so their network waits cannot starve the control reactor or script host.
- Connection watch gates on Connected status AND client presence. It compares effective client Arc identity/status so normal health updates do not reload scripts. Connection loss cleans output/display/script activation immediately; same-train reconnection restores it without relying on a new TrainChanged event. TrainChanged activates all three auxiliary controllers.
- A 250ms revision watcher captures baseline before startup becomes visible and reconciles committed trains/bindings/scripts/hardware/settings edits from UI, MCP or REST. Settings commits reconfigure the owned simulator connection. Current implementation reloads all controllers after any watched topic change; fine-grained reloads are an optimization.
- Desktop hardware consumers directly dispatch ordered actual port/generation/config/pin values to train controllers and VjoyManager. Acknowledged per-port suspend/source-loss/resume uses controller APIs from the script agent. Source generations are checked; a verified fresh input after lease release resumes routing.
- LiveHardwareEffects uses root's cloneable HardwareCommandPort, so effect writes and lease callbacks do not reenter the HardwareRuntime handle mutex. A shared gate holds across acknowledged serial writes. Suspend waits preceding writes, fences every producer, sends actual LOW and blank messages for configured outputs/displays, then acknowledges lease transfer. Resume invalidates controller caches. Output controller now caches only successful writes so failed/suspended sends retry.
- vJoy desktop pump seeds current connected generations from the hardware cache/resolver, observes committed vjoy/bindings/hardware revisions and drives recovery deadlines. Shutdown stops that pump and neutralizes without clearing persisted enable. **Pending final release-runtime API from vJoy agent:** `neutralize_outputs` currently does not release acquired native handles; `disable` is intentionally not called because it persists enable=false.
- MCP now receives LiveSimulator and real InputDetectionSession-backed detection ports. Detection emits/clears a prompt, uses authoritative hardware baselines/type thresholds and returns actual stored identity/device fields.
- Desktop registers actual controls, vJoy, hardware, MCP and upload shutdown participants. UI admission stops before producer cleanup; hardware samples stop dispatching during shutdown. ControlRuntime retains ownership on failed/timed-out shutdown and supports later retry. Root/script agent are hardening TrainService pump joins separately.
- Firmware uses root's `new_with_serial_ownership`, runtime_upload handoff adapter and event/reconnect hooks. Shutdown cancellation propagates Timeout/CleanupIncomplete and retries retained cleanup. UI cancellation distinguishes these from NotFound.
- REST compatibility API supplied by root is attached to the same Arc<Ports>/database on the MCP HTTP server. `/shutdown` invokes AppHandle.exit through the existing coordinated ExitRequested flow.
- New commands registered: `ui_run_script`, `ui_get_script_log`, `ui_get_connected_devices`, `ui_get_simulator_status`, `ui_retry_simulator`. Preview agent's five commands are registered and calibration start derives ceiling from Rust persistence/default instead of trusting caller.

## Composition adversarial round 1 fixes

The initial test failed to compile until the extracted adapter existed; the assertions target the reviewed old behavior (empty current-DB list would incorrectly acknowledge the lease).
2. **Failed key release remains owned.** KeyboardOwnership now clears only successfully released keys. Shutdown retains failed key/holder associations; ordinary release and owner_gone also retain failures so cleanup cannot forget them before shutdown. A fake adapter regression was observed failing on holder count zero before the fix; after the fix the second shutdown actually sends key-up and then clears ownership. Updated the older test that explicitly expected failed release bookkeeping to be discarded.
3. **Native helper actions are bounded and reaped.** Replaced Command.output with a 2-second action deadline, 64 KiB captured output maximum, bounded nonblocking pipe reads and no pipe-reader threads/EOF joins. Unix children run in an owned process group; Windows children are assigned to a kill-on-close Job Object. The direct child and remaining descendants are terminated on completion/deadline and the direct child is reaped. Regression tests initially failed for a two-second hanging action reporting success and for a descendant-held pipe delaying success. Green tests prove timeout, direct child gone/reaped, uncertain press ownership surviving for key-up cleanup, bounded verbose output, fast parent exit despite lingering descendant pipes and concurrent NativeKeyboard shutdown waiting for the bounded in-flight press then actually releasing the key. The deadline was set to 2 seconds (rather than the initial 500 ms experiment) because normal shell startup under concurrent compilation exceeded 500 ms; the tests still distinguish a five-second blocked child/descendant from bounded behavior.
4. **Initial connection snapshot is delivered.** The production connection watch is initialized through `connection_updates`, which marks the current snapshot changed before the select loop. A unit test constructs an already-connected receiver with no future send; it failed with a 50 ms timeout before the fix and now processes the snapshot immediately. This is equivalent to the slow-construction race without inserting production startup delays.
