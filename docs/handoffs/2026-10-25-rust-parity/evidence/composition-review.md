# Production composition review

Read-only review of Task 5 live composition, output/display hosts, desktop callbacks/upload linkage and `tests/composition.rs`. The handoff reports 3 composition, 30 output/display, 10 script and 14 desktop tests passing. The script agent owns the in-progress acknowledged manual-run API; that is excluded here. The vJoy shutdown release was changed during review: current `VjoyRuntime` calls `stop_admission` then `release_runtime`, preserving the persisted requested flag and retaining native handles after a failed neutralization. That addresses the original native-handle shutdown gap on inspection; its two focused tests are reported by the parent.

## Verdict

**Spec:** The shared resolver, arbiter, runtime adapters, committed revision watcher, effective-client gate, MCP live simulator/detection and actual UI registrations are present. **The live chunk needs fixes before integration** for lease neutralization and acknowledged key cleanup. **Quality:** The loopback test proves a useful activation/input/effect/reload/disconnect path, but it has no changed-output-before-lease, failed-key-release/retry, slow native sidecar, or already-connected startup case. Fake success on the exercised path does not establish those lifecycle barriers.

## Findings

1. **Critical — a just-deleted or moved output can remain HIGH when a serial lease is acknowledged.** `tauri/src-tauri/src/rust_ui.rs:3147-3198` takes a per-port send gate and drives LOW for outputs returned by the *current* `outputs_for_device` query. It does not retain pins that were successfully driven HIGH earlier. Reproduce: while an output at pin 4 is HIGH, commit an output deletion or pin reassignment and acquire a calibration/firmware lease before the 250 ms revision watcher (`composition/mod.rs:110-111`) reloads the output controller. `suspend` sees only the new DB snapshot and omits pin 4, then acknowledges the lease. The delayed output cleanup cannot send LOW through the suspended gate. The physical output can therefore remain actuated throughout another owner's lease. **Test:** fake serial reports, hold pin 4 HIGH, commit the removal, immediately acquire a lease, and assert a LOW for pin 4 precedes lease acknowledgement. Track successfully actuated pins in the live effect adapter and neutralize their union with current persisted outputs; retain failed neutralizations for retry.

2. **Important — failed native key release is forgotten, so a retry can falsely acknowledge shutdown.** `composition/keyboard.rs:41-42` delegates shutdown to `KeyboardOwnership::shutdown`. Its `keyboard.rs:447-462` release loop records errors but then clears both `held` and `holds`. If the sidecar fails both key-up attempts, the first `ControlRuntime` shutdown reports an error, but the next shutdown sees no held keys, returns success, and permits network/DB closure while a key remains physically down. **Test:** fake adapter succeeds on key-down, fails two key-up attempts, then succeeds; call the composition keyboard shutdown twice and require the second call to retry key-up before success. Keep failed release ownership until acknowledged or explicitly report unrecoverable state on every retry.

3. **Important — native keystroke subprocess execution has no deadline or reap on a hang.** `keyboard.rs:295-299` calls `Command::output()` synchronously. `NativeKeyboard` holds its mutex during this call (`composition/keyboard.rs:41-54`); button input or shutdown can block there indefinitely. `ControlRuntime::cancel_and_join_producers` has a 20 second outer timeout (`composition/mod.rs:153-163`), but it retains a permanently stuck host and cannot complete coordinated shutdown. **Test:** point the trusted executable probe at a fake child that never exits, press a mapped key, then request shutdown; require the child to be killed/reaped within a bounded deadline and retryable cleanup to complete. Give each action a subprocess deadline, kill and reap the child on expiry, and propagate the failure without losing the held-key state. This is a release-blocking lifecycle issue, rather than a harmless documented residual.

4. **Important — startup can miss the already-connected status snapshot.** `composition/mod.rs:68-85` starts the connection owner, builds several services, and only then calls `connection.latest()` and waits on `status.changed()`; it never processes the receiver's current value. If the initial 1 second connection completes before line 79 on a slow startup, this new receiver starts with a `Connected` snapshot considered seen. No later status change occurs until the 30 second health check, so `effective_client` stays `None` and train detection/controllers/scripts remain inactive. **Test:** make runtime construction take longer than the initial connection delay while loopback `/info` succeeds, then assert train detection/effect activation promptly after `ControlRuntime::start`. Process the initial `borrow_and_update()` snapshot before entering the select loop.

## Checked paths and limits

- The IO bridge has a 64-slot queue, enqueue-to-completion deadline and shutdown cancellation; the connected-client view checks both status and client presence. No unbounded async/sync bridge wait was established there.
- Hardware dispatch checks current port generation before delivering a sample (`hardware/service.rs:1250-1303`), and the desktop path resumes a suspended port only on that accepted fresh sample. `source_lost` fences a late old generation.
- The composition test does not cover an actual desktop `AppHandle`, Windows driver, physical serial output or installer. Those remain integration acceptance, not additional counted defects in this report.
