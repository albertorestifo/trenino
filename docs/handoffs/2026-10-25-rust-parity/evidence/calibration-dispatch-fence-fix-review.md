# Calibration dispatch fence — focused fix review

## Verdict

**Original Important partial-resume finding: ADDRESSED.** No new Important or Critical regression was established in the scoped input change. The desktop still has a per-port physical output gate; it now also sends lever and button samples through a port-specific cache-only path whenever that port has an output suspension, active resource lease, or recorded source-neutralization failure. A failed aggregate resume can leave both workers internally resumed, but subsequent samples for the retained lease carry `observe_only` and cannot become ordinary controller effects.

## Checked behavior

- `AppHardwareConsumers::dispatch_port_input` consults the actual shared arbiter and suspension set, attempts resume only when the port has no lease/failure, recomputes the gate afterward, and dispatches through `composition::input::dispatch_control_input` (`tauri/src-tauri/src/rust_ui.rs:1124-1164`). A failed resume is returned after cache dispatch and hardware event publication (`:1138-1149`, `:1166-1195`), so the error remains visible without losing the observed level.
- `port_is_fenced` checks only the named port's suspension, active lease, and neutralization failure (`crates/trenino-runtime/src/composition/input.rs:12-22`). It avoids global `is_suspended`, leaving an unrelated port available. `dispatch_control_input` tries both controller queues and reports queue errors (`:23-60`).
- Cache-only intent is part of each queued sample (`lever_controller.rs:317-330`, `button_controller.rs:372-382`), so a sample admitted during a lease stays cache-only even if worker resume happens before dequeue. Both workers process it as a baseline and run per-port cleanup; they return before simulator/key effect code (`lever_controller.rs:717-749`, `button_controller.rs:892-925`). Normal input at the same cached level stays quiet after release; a new value or edge can act. Activation/release clears the baselines, and their recorded port/generation prevents stale equality matches.
- The worker control loops prioritize suspend/resume commands over queued samples (`lever_controller.rs:561-648`, `button_controller.rs:734-809`). Previously admitted normal samples are processed under the worker's suspended-port state after an acknowledged suspension; later cache-only samples keep their immutable queue tag. Per-port cleanup filters pending writes, sequences, repeats and held keys by source port, rather than draining another port's work (`lever_controller.rs:666-703`, `button_controller.rs:832-880`).

The focused integration regression in `tests/control_dispatch.rs:1717-1909` exercises the actual arbiter and controller workers with a failed final resume, cache-only levels, unchanged-level non-replay, fresh changes after retry, and live COM2 actions while COM1 is leased. The second regression at `:1912-2024` covers a suspension failure before button suspension and cache-only cleanup of a held key. The pure gate test covers per-port source failure. I inspected those tests and the production call path; I did not rerun the owner's reported workspace 840, controller 34, desktop 37, and UI 165 green suites. No source files were edited.

Cache-only cleanup itself is asynchronous worker processing, not a new synchronous cleanup ACK. If native key release or task cancellation fails, existing retained cleanup/error paths still govern that failure; this fix does not declare that work settled. That boundary does not reproduce the original partial-resume actuation defect.
