## Important remaining findings

1. **The conservative physical-effect ledger is never drained during application shutdown.** `tauri/src-tauri/src/rust_ui.rs:1171-1172` implements `HardwareRuntime::neutralize_and_release_outputs` as unconditional success despite owning `effects`. `ControlRuntime`'s same phase is also a no-op (`composition/mod.rs:171-173`). Its producer shutdown invokes controller cleanup, but the output controller only visits its current binding map and ignores send failures (`train/output_controller.rs:326-344`); script cleanup clears VMs/subscriptions without neutralizing script outputs (`train/script/runner.rs:598-609`). Manual output/display commands now correctly write through `hardware.effects` (`runtime_hardware.rs:63-89`), but have no controller cleanup owner. Thus a manual/script HIGH, a deleted binding, or a failed controller LOW remains in the ledger when shutdown proceeds.

   **Concrete reproduction:** on a fake connected board, use the production manual-output command to set an output HIGH with no simulator output binding (or execute `output.set(id, true)`), then request coordinated shutdown with no calibration lease. No phase calls `effects.suspend(port)`, so no LOW precedes serial close. `HardwareServiceHandle::shutdown` first sets the stopping flag and shuts the scanner (`hardware/service.rs:1134-1153`); attempting cleanup later cannot send through that command port. The closing event is not a fallback: `mark_source_lost` removes the current port before calling consumers (`:1634-1675`), and desktop `source_lost` only calls `effects.suspend` if the generation remains present (`rust_ui.rs:944-963`).

   **Required targeted test/fix:** wire an acknowledged ledger-drain operation into the hardware participant's neutralization phase while serial writes remain admitted. Fake HIGH/nonblank -> shutdown must emit LOW/full blank before serial close; inject a failed cleanup acknowledgment and require shutdown failure with pending targets retained, then successful retry. Include manual/script targets absent from current controller/DB bindings. This finding is established from production control flow; no real serial shutdown was performed.

2. **A failed serial shutdown discards its owning handle, so the next attempt falsely succeeds.** `rust_ui.rs:1174-1178` calls `self.handle.lock().take()` before `handle.shutdown()?`. On any error the local handle is dropped and the slot remains `None`; retry therefore returns `Ok(())` without invoking cleanup again. The lower-level owner intentionally supports retry: `hardware/mod.rs:677-690` returns `TimedOut` while retaining its join handle and explicitly reports that open ports remain owned. `HardwareServiceHandle::shutdown` propagates that scanner failure immediately (`hardware/service.rs:1150-1153`). The desktop wrapper defeats this contract and may permit later shutdown phases/database close after the second request while serial ownership is still unresolved.

   **Concrete reproduction/test:** inject a serial owner whose close exceeds the discovery cleanup deadline. First `HardwareRuntime::close_ports_and_network` returns an error; keep the owner blocked and call it again. Current code sees `None` and succeeds. Retain the handle in its slot on error; remove it only after an acknowledged successful shutdown. Require retries to continue failing until the owner exits, then join successfully once.
