# vJoy configurator review — 2026-10-25

Read-only source review of Task 2, the retained joystick/platform contracts, the legacy configurator/system adapter and tests, and the new portable/native configurator plus manager integration. No driver, registry, elevation, user database, or physical hardware was touched. The supplied isolated Windows type-check is useful compilation evidence; it does not establish the native lifecycle guarantees below.

## Verdict

**Spec: needs fixes. Quality: needs fixes.** Explicit selected-ID arguments, descriptor validation, per-ID markers (including legacy ID 1), normal busy/foreign deletion rejection, missing-marker cleanup, 1223 mapping, startup without UAC, and non-persisting `release_runtime` are implemented. The important gaps below prevent accepting the privileged lifecycle. No Critical finding is claimed.

## Important findings

1. **The deadline starts before UAC, and late successful elevation is treated as failure without reconciling its effects.** `crates/trenino-runtime/src/vjoy/configurator.rs:200,208-210` starts the budget before initial probe; `run_bounded` at lines 38-46 explicitly includes `spawn`/consent. `windows_configurator.rs:220` synchronously runs `ShellExecuteExW`. The retained contract is more precise than the implementation note: `docs/superpowers/plans/2026-10-24-rust-joystick.md:129` says **“Scope the deadline after UAC acceptance”** and requires reconciliation after completion/timeout. Reproduce with a missing selected device: leave UAC open >10 seconds, then accept. The helper is launched, but the caller immediately tries to terminate it and returns Timeout; even an already-exited successful helper is rejected. `create` never checks whether the device appeared and never records ownership. A created device can therefore remain without its recovery marker, while the UI reports failure. This is not a request to preempt the consent UI: start the post-consent deadline at the specified boundary and reconcile uncertain outcomes before accepting another operation. **Targeted test:** delayed consent followed by successful helper creation must receive its full post-consent budget and preserve ownership/cleanup diagnostics. The existing `late_launch` test asserts the incorrect policy.

2. **The Windows status probe ignores its deadline and can monopolize the owner indefinitely.** `crates/trenino-runtime/src/vjoy/windows_configurator.rs:286-300` discards `_budget_ms`, then runs filesystem/DLL loading and SDK calls synchronously. `checked_status` (`configurator.rs:313-315`) can only check time after those calls return. A stalled driver probe (including after privileged re-enumeration) therefore prevents the promised bounded status poll, and the manager holds its single mutex throughout the call (`manager.rs:271-283`, `1000-1090`), preventing `stop_admission`/`release_runtime` from progressing. The portable slow-status fake implements its own timeout; it does not verify the native boundary. Retained `rust-joystick.md:7,47,115-118,129` explicitly keeps fault isolation and a bounded native worker/probe. **Targeted test:** an isolated fake SDK blocks a status call past its budget; the owner must return a typed timeout and retain/reap its worker without blocking subsequent cleanup. A full Windows workspace check is not required to establish this structural defect, but actual driver timing remains untested.

3. **Timeout cleanup does not meet the process-tree/retained-cleanup contract.** `windows_configurator.rs:251-258` implements `terminate_tree` with `TerminateProcess` on only one handle; it does not cover descendants. `configurator.rs:44-45,52-53` uses `?` on termination, so any termination error skips `reap`; `NativeChild::drop` then merely closes the only handle (`windows_configurator.rs:166-171`). The elevated operation can continue after an error with no retained process ownership or outcome reconciliation. Even successful termination uses another fixed 5-second wait (`windows_configurator.rs:261-265`), outside the stated single operation budget. Microsoft documents that terminating a process does not terminate its children, and that `TerminateProcess` is asynchronous and requires PROCESS_TERMINATE rights: [process termination](https://learn.microsoft.com/en-us/windows/desktop/ProcThread/terminating-a-process), [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess). No claim is made that the specific pinned helper necessarily spawns children, or that all ShellExecute handles lack terminate rights. The failure path itself demonstrably loses ownership. **Targeted tests:** inject termination failure and require retained cleanup/reconciliation rather than dropping the child; on Windows use a harmless helper spawning a delayed sentinel child and prove neither survives timeout. Surface CleanupIncomplete while retaining handles when termination/reap cannot be acknowledged.

4. **Compatible foreign devices bypass the required ownership conflict policy.** `configurator.rs:201-202` returns success for Compatible without consulting `owned`; `manager.rs:1069-1073` likewise acquires any Free/Owned compatible selected device without checking the persistent marker. `cleanup_selected` at `manager.rs:1135-1136` silently skips unmarked devices, so disabling also reports success instead of the required conflict. `rust-joystick.md:130` explicitly says a compatible pre-existing unowned device is a conflict with no automatic adoption, and disable must release local acquisition and report the conflict. This also hides a marker-write failure on retry: create succeeds physically, marker persistence fails, retry sees Free and becomes Active without recovery ownership. The new tests only ensure foreign Free is not a leftover; they do not exercise enable/retry/disable. **Targeted tests:** selected Free+unmarked -> enable/create ForeignDevice, no acquisition; marker write failure -> retry must preserve an explicit cleanup/conflict state; disabling an already acquired foreign device must release it, never delete it, and report the conflict.

5. **Trust validation misses linked/reparse ancestors above the derived installation anchor.** `configurator.rs:143-160` starts probing at `paths.anchor`; it never checks any parent of that anchor. `windows.rs:56-64` derives that anchor as `resources.parent()` rather than retaining an independently established higher trust anchor. For `/installed/link/Trenino/resources/vJoyConfig.exe`, where `/installed/link` is a symlink/junction, lstat of `/installed/link/Trenino` and its descendants reports ordinary directories/files, so the helper and DLL are accepted and used outside the asserted installation tree. Windows `symlink_metadata` checks the final component, not intermediate reparse components. The same check gates `driver_available` (`windows.rs:117-129`) and elevation. Task 3's adversarial reparse-ancestor requirement (`rust-joystick.md:127`) is not covered by the current test, which only changes the anchor itself or a child. **Targeted test:** mark a strict ancestor of the supplied anchor LinkOrReparse while all final components are regular; expect UntrustedResource and no SDK load/elevation. Validate the full relevant ancestor chain from an independently trusted root, not a trust root derived solely from the resource path.

## Reproducible evidence and limits

A standalone Rust harness at `/tmp/trenino-vjoy-review-probes.rs` imports the actual current `configurator.rs` (no rewritten implementation). Run:

```sh
rustc --edition 2021 --test -Awarnings /tmp/trenino-vjoy-review-probes.rs -o /tmp/trenino-vjoy-review-probes
/tmp/trenino-vjoy-review-probes --nocapture
```

**Executed: 4/4 observed-bug probes passed:** foreign compatible create returns success; consent delay of 10,001 ms rejects an otherwise successful helper; termination error skips reap; strict ancestor LinkOrReparse is accepted. These assert the observed bad behavior, not acceptance criteria. The small harness did not load native code. Existing portable configurator tests were inspected, not repeatedly rerun. Windows SDK/driver/elevation smoke remains unavailable on this Mac; no unverified real-OS result is represented as passing.

The normal selected-ID create/delete argument path is fixed and does not enumerate or mutate unselected IDs. `release_runtime` retains failed neutralizations and does not call deletion or persist enable=false. No additional finding is raised against those paths.
