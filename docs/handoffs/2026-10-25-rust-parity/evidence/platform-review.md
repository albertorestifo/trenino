# Platform parity / simulator owner / upload ownership review

Scope: Task 1 recovered storage, catalog, executable and hardware changes; Task 3 simulator connection owner; Task 5 firmware upload ownership seam and new desktop `runtime_upload.rs`. Runtime composition and UI are reviewed separately. Read-only inspection; no unchanged suites rerun. The handoff reports focused green suites in `tmp/connection-foundation-final.log`, `tmp/upload-handoff-final.log`, and `tmp/parity-fixes-tests.log` after the named fixes.

## Verdict

**Spec:** Most requested parity helpers and the serial handoff protocol are present. The scanner's reservation prevents a new bootloader port from being opened while firmware owns a handoff, and the desktop adapter retains uncertain operation IDs for retry. **Not ready to accept as a fully bounded lifecycle chunk** because disconnect cannot cancel an in-flight health request, and cancellation can acknowledge before serial cleanup has finished.

**Quality:** The focused tests exercise initial connection attempts, stale connect results, renamed bootloader ports, and successful/failed handoff cleanup. They do not exercise disconnect during a health probe or a cancellation whose terminal cleanup retains the lease. No new source edits or test runs were made in this review.

## Important findings

1. **Disconnect/reconfigure/shutdown cannot preempt an in-flight health HTTP call.** The owner stores initial/retry connection calls in an abortable `attempt`, but the health branch awaits `current.with_fast_timeouts()?.info().await` inline in the only worker (`connection_owner.rs:230-245`). The command branch is not polled during that await. At the 30-second health tick, hold the `/info` response; call `disconnect().await` or `reconfigure().await`. Those methods return after queue admission (`connection_owner.rs:132-142`), while `latest()` remains Connected and the old health result can publish Connected before the queued command is processed. Shutdown also waits for the one-second fast HTTP deadline rather than canceling it. This misses Task 3's in-flight HTTP lifecycle barrier. **Test:** hold a health response, request disconnect/reconfigure/shutdown, and assert the latest status changes and the old request is dropped before releasing that response. Health should be an owned cancellable attempt or selected against commands with an acknowledged lifecycle transition.

2. **`cancel_upload` reports success even when serial cleanup/lease release is incomplete.** `finalize_upload` correctly records a failed `owner.finish` and retains the lease for `retry_cleanup` (`upload.rs:1180-1212`), but it clears `state.current` and publishes a terminal record (`:1334-1343`). `cancel_upload` only waits for `current` to disappear and then returns `Ok(())` (`:1691-1727`); its own comment promises that the port reservation is released once it returns. On its timeout path it also returns `Ok(())` while the worker is still unwinding (`:1713-1719`). **Test:** fake an ownership `finish` failure, cancel the upload, then assert `cancel_upload` returns a cleanup-incomplete error and the lease stays held until `retry_cleanup` succeeds. Repeat with a blocked finish beyond the cancellation deadline. The caller needs an explicit uncertain result rather than a false clean acknowledgement.

## Residual observations

- `ManagerLifecycle::drop` only joins a currently active upload (`upload.rs:1467-1490`). Once a cleanup failure has made the upload terminal, dropping the last manager handle discards its `pending_cleanup` record even though the scanner pin and arbiter lease remain. The composition shutdown owner must retain the manager and call `retry_cleanup` before dropping it; a dedicated shutdown result would make this enforceable. This is related to finding 2 rather than a separate counted defect.
- Catalog token headers, compatible release selection, manifest/asset URL checks, filename detection, blank validation, grapheme length, manual scan backoff bypass, and the owned post-upload scan match the intended paths on inspection. The Windows executable probe accepts an absolute file from the configured/app-resource tier and excludes development/PATH candidates in release; no separate path-trust defect was established within this chunk. The concurrent platform edit now uses Unix-gated errno values and `ErrorKind` elsewhere for port error formatting (`hardware/mod.rs:93-113`), so the earlier numeric Windows concern no longer applies.
