# vJoy live runtime adversarial review

Scope: Task 2 live reporting in `vjoy/{manager,mapper,adapter,windows}.rs`, `tests/vjoy_live.rs`, `tests/vjoy_manager.rs`, and the two MCP match arms. Compared with the legacy `virtual_joystick/{manager,mapper}.ex` and its tests. The Windows configurator, installed helper ownership, and desktop wiring are separate residual scope.

## Verdict

**Spec:** The mapper's eight oracle cases, selected-device acquire/report path, cache while off, basic per-port loss, and bounded recovery behavior are present. The live chunk is **not ready to integrate**: a mapping reload can drive vJoy while the shared resource lease is suspended, and failed reload can later republish a deleted mapping.

**Quality:** `cargo test -p trenino-runtime --test vjoy_live --test vjoy_manager --no-default-features` passes (14 + 24 tests). Those tests do not cover lease overlap with reload, failure during deletion reload followed by recovery, or two ports carrying the same config/input identity. Windows `set_axis`/`set_button` uses the vendored one-based IDs and its `get_device_state` → `update_device_state` contract correctly on inspection (`vendor/vjoy/src/vjoy.rs:193-249`, `vendor/vjoy/src/device.rs:125-169`); native execution remains unverified in this checkout.

## Important findings

1. **Mapping reload bypasses a held arbiter lease and reasserts cached controls.** Live input checks `!self.arbiter.is_suspended()` at `manager.rs:402`, but `reload_mappings` at `manager.rs:545-575` calls `publish_current_state` with no lease check. `publish_current_state` at `manager.rs:690-705` sends cached non-neutral values. Reproduce: activate with a cached pressed button or deflected axis; acquire a calibration/firmware lease and neutralize the device; call `reload_mappings` after a DB change while the lease remains held. The cached pressed/deflected report is sent again. This violates Task 2 lease fencing and can actuate during calibration/firmware ownership. **Test:** hold an arbiter lease, neutralize, reload, and assert every report while the lease is held is safe; only a fresh post-lease sample may reassert. Safe releases of deleted targets may proceed, but current values must wait for resume.

2. **A failed deletion reload leaves the old mapping in runtime and recovery republishes it.** `reload_mappings` builds the new snapshot, then sends safe values for removed targets before installing it (`manager.rs:545-569`). If any safe report fails at `:562-565`, `runtime_loss` is entered and the method returns while `inner.mappings` still contains the deleted target. After the adapter recovers, `poll_recovery_at` calls `publish_current_state` against that old snapshot (`manager.rs:333-356`, `:690-705`), so the deleted target can be driven again. Reproduce: press a mapped button, delete its mapping in DB, force the fake adapter to fail the safe report during `reload_mappings`, clear the failure, then run the due recovery attempt; the manager becomes Active and sends a pressed report for the deleted mapping. **Test:** exactly this sequence; assert deleted targets are absent after recovery and no input can report through them. Keep the new snapshot/pending deletion authoritative even if the safe write fails.

3. **Suspending one port can neutralize a target still supplied by another live port.** `source_lost` explicitly checks `owned_elsewhere` by `input_id` before sending a safe value (`manager.rs:498-504`), but `suspend_port` sends safe for *every* mapping with that config ID (`manager.rs:515-540`). Two connected ports can share a config/identity; an unsampled or stale COM2 that is suspended will release the button currently pressed through COM1. Reproduce: `input_value("COM1", same_identity, pressed)`; `observe_port("COM2", same_config)`; enable; clear adapter events; `suspend_port("COM2")`; observe an unexpected button release. **Test:** two ports with the same config, one supplying the mapped input; suspending the other must preserve its report. Use the same per-mapping ownership check as source loss, with a defined active-port policy.

4. **A higher port generation drops cached ownership without neutralizing its old targets.** `input_value` and `observe_port` replace `LivePort` when the generation or config changes (`manager.rs:393-400`, `:461-468`), but issue no safe reports for values from the prior generation. Reproduce: report a pressed button at generation 7; call `observe_port` for generation 8 before any generation-7 `source_lost`; send no fresh button sample. The button remains pressed indefinitely even though the old generation is no longer accepted. This matters on reconnect/reconfiguration paths where the new generation is observed before the loss callback is processed. **Test:** assert a generation handover safely releases old cached mapped values and rejects late generation-7 samples; if source-loss ordering is a strict precondition, enforce it at this API boundary.

## Additional review notes

- The mapper result matches the legacy `round` semantics in the tested cases, including reversed bounds and midpoint 16384. No Windows axis/button ID mismatch was found in the vendored APIs.
- The existing `disable` path discards a `release_all` neutralization error when DB persistence succeeds (`manager.rs:240-250`). This predates the live chunk, so it is not counted above, but it remains a safety/status issue for the overall manager.
