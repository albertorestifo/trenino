# SCRIPT RUNNER + SEQUENCE adversarial review

Scope: `train/script/runner.rs` and its export, `train/sequence.rs`, `train/button_controller.rs`, `tests/script_runner.rs`, and the scoped `control_dispatch.rs` test change. Compared with Task 3 of `docs/superpowers/plans/2026-10-25-rust-parity-completion.md` and the legacy script runner / button controller. No production composition findings included.

## Verdict

**Spec:** Not ready to integrate as a completed Task 3 chunk. The routine polling, effects, reload, and sequence paths are represented, but timer replacement, documented subscription range, and bounded owned-task shutdown have unresolved counterexamples.

**Quality:** Focused suites pass (`cargo test -p trenino-runtime --test script_runner --test control_dispatch`: 6 + 28 passing), but tests cover only noncolliding deadlines and ordinary port completion. The defects below need targeted regression tests and fixes before the chunk is accepted.

## Findings

1. **Important — a replaced schedule can still run when its old deadline coincides with a poll.** `runner.rs:379-412` snapshots all due timers, puts `Poll` first, then executes each snapshot item without checking that its deadline is still current. At `t=0`, manually run a script whose `on_change` schedules `200` ms. Give its trigger a changed value. At `t=200`, the poll runs first and the same script can replace the schedule with a later deadline, but the already-snapshotted `Due::Scheduled` still fires immediately. This breaks `schedule`'s replace/cancel rule in legacy `script_runner.ex:410-418` and can emit an unexpected `scheduled` effect just as a reload or state change is pending. **Test:** FakeClock with a poll and scheduled callback both due at 200 ms; have the trigger execution replace the callback with 500 ms; assert no scheduled log/effect before 700 ms. The due item should carry the original deadline or generation and be revalidated before execution.

2. **Important — positive submillisecond `schedule` requests create an immediate self-running loop.** The existing engine records `schedule(0.5)` as `Schedule { ms: 0 }` (`engine.rs:806-815`); `runner.rs:704-708` turns that into `now`, and `next_deadline` / `fire_due_timers` (`runner.rs:296-308`, `:361-412`) immediately execute it again. A script that reschedules itself this way can consume a host CPU continuously, grow the VM replay history and log without bound, and delay queued lifecycle commands. The legacy code also truncates this input, but Task 3 expressly calls for bounded owned tasks and failure containment. **Test:** manually run `function on_change(e) schedule(0.5) end`, use a FakeClock that never advances, and assert a bounded number of invocations plus prompt acknowledged shutdown. Reject/normalize zero-delay schedules or otherwise yield and bound them.

3. **Important — the documented subscription ID partition is not enforced.** `runner.rs:481-486` assigns `2000 + index` to every unique endpoint. With 1,001 trigger endpoints, the final ID is 3000, outside the script range `2000-2999` declared at `runner.rs:68-70` and overlapping the display controller's range. This can overwrite or unsubscribe another controller's subscription. The handoff notes the gap; it remains a direct correctness issue in this chunk. **Test:** load 1,001 unique endpoints and assert no subscribe/unsubscribe call with an ID outside 2000-2999; verify an explicit load error or a defined overflow policy.

4. **Important — controller death does not cancel a sequence command already awaiting HTTP.** `sequence.rs:143-160` checks owner liveness before `set_async` and watches it only during the subsequent delay. If all controller handles are dropped while `set_async` is pending, the worker drops the owner sender, but the sequence remains in that future until the HTTP call completes. Explicit route cleanup aborts tracked tasks, but owner loss alone does not meet the documented monitor behavior or Task 3's bounded owned-task requirement. **Test:** use a `SequenceSimulator` whose `set_async` stays pending, start a run, drop the owner sender, yield, then assert the run finishes and no completion is sent. Select owner closure against the HTTP future too.

5. **Important — script shutdown can wait indefinitely on a synchronous injected port.** `runner.rs:481-486`, `:504-507`, `:541-543`, and `:718-720` call subscription/effect ports synchronously on the sole runner host. `shutdown()` at `runner.rs:257-270` awaits its mailbox reply and then joins the thread without a deadline. A stalled `get_subscription`, `subscribe`, `unsubscribe`, or `api.set` blocks all commands and makes shutdown unacknowledgeable. This violates Task 3's bounded, retryable acknowledged shutdown independent of the choice of production adapter. **Test:** block a fake subscription fetch or effect send, request shutdown under a short timeout, and assert a defined timeout/error and no retained host. Port operations need enforced deadlines or another cancellable ownership arrangement.

## Coverage observations

- The six runner tests use an always-connected, always-successful simulator (`tests/script_runner.rs:29-58`). They do not cover failed subscribe, disconnected activation followed by connection, disabled/deleted scripts after reload, simultaneous poll/schedule deadlines, or a port stalled during shutdown. The current failed-subscribe bookkeeping at `runner.rs:481-486` matches the legacy oracle's kept ID/no retry behavior; it is not separately counted as a parity defect.
- The scoped `control_dispatch.rs` timing assertion correctly waits for sequence completion rather than racing the second HTTP request. Existing sequence tests exercise release and train-switch cancellation, but not owner loss during an in-flight `set_async`.
