# vJoy configurator fix 1 scoped re-review — 2026-10-25

Source review of the five findings in `tmp/vjoy-configurator-review.md`, the replacement configurator/native process/status-worker implementation, manager integration, early desktop entry, and focused tests. No source changes or native device/elevation/registry actions.

## Verdict

**Needs fixes.** The post-consent deadline, root-to-resource trust walk, ordinary unmarked-device conflict, and retaining handles on cleanup failure are present. Three original guarantees remain incomplete in production, and the new marker checks introduce a rollback hole. Four Important findings follow; no Critical severity is claimed.

## Important findings

1. **A pre-launch pending marker is treated as ownership evidence and can authorize deletion of a foreign device.** `configurator.rs:262` persists pending intent before calling elevation. After a crash while consent is open/before launch, that marker says nothing about whether Trenino ever created a device. Nevertheless `create` promotes any Compatible pending device (`:248-251`), `delete` promotes then deletes it (`:303-312`), and `reconcile_create` promotes it even after a definite launch error (`:426-440`). A different application can create the missing selected ID during that interval or after the crash. Retry/Remove Leftover then silently adopts or deletes that foreign compatible device. This violates the retained rule that ownership is set only after **this operation** creates an absent device; compatibility plus a recorded intention does not prove causation.

   **Two executed actual-source regressions are RED:** `/tmp/trenino-vjoy-fix1-review-probes.rs` imports current `configurator.rs` and reuses the actual test fake. `review_stale_prelaunch_intent_authorizes_foreign_deletion` sets a pending marker left before launch, supplies a later foreign Compatible device, calls delete, and receives `Ok(())` instead of `ForeignDevice` (the fake helper accepts the destructive `-d 7`). `review_failed_launch_must_not_adopt_new_foreign_device` supplies Missing before launch, a definite Native launch failure, then Compatible from an external creator; current code returns success and records ownership. Keep unconfirmed intent distinct from confirmed creation provenance. Uncertain stale pending state must remain a conflict/diagnostic, never automatically authorize deletion; known pre-launch failures must not promote ownership. Confirmed-helper-success/marker-write-failure recovery needs its own durable stage.

2. **Elevated helper containment is established after the helper is already executing.** `windows_configurator.rs:256` launches the real privileged `vJoyConfig.exe` with `ShellExecuteExW`; only at `:280` is that running process assigned to its Job Object. A descendant created before assignment is outside this job. A successful assignment sets `contained=true` anyway; job accounting can reach zero while that escaped child still runs, allowing Timeout/success or later cleanup acknowledgement with outstanding mutation. This is the same spawn-before-job race fixed in the keyboard module, still present at the privileged boundary. [Microsoft's Job Object contract](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) inherits the parent's job for children created **after** association; assignment is not a retroactive process-tree capture.

   **Targeted Windows reproduction:** use a harmless elevated helper that immediately starts a delayed sentinel writer; widen the interval after ShellExecute returns but before assignment, then expire the operation. Assert no sentinel runs after cleanup acknowledgement. No Windows execution was performed here, and no claim is made that the pinned helper always spawns children. To satisfy the explicit process-tree guarantee, arrange containment before helper code runs (for example an elevated same-executable broker that launches the actual helper suspended, assigns it, then resumes). The newly retained handles correctly improve failure recovery but cannot account for descendants that never joined the job.

3. **The bounded status worker is bypassed by production setup preflight.** The new `ConfiguratorBackend::status` child and early `main` dispatch are wired correctly, but `VjoyManager::enable`/startup still execute `adapter.driver_available()` at `manager.rs:1041` and `adapter.device_status()` at `:1089` **before** entering `configure_create`. `WindowsVjoyAdapter::driver_available` directly loads/initializes the DLL and calls `is_enabled` (`windows.rs:126-146`); `device_status` directly calls the native SDK (`:154-158`). These happen under the manager mutex with no process boundary or deadline. A stuck driver/DLL probe therefore still blocks setup and `stop_admission`/`release_runtime` indefinitely, before the new bounded probe can run. The original finding concerned that production owner-lock failure, not only the body of the configurator trait method.

   **Targeted regression:** a fake/native SDK whose initial enabled/status call blocks must cause production manager enable/startup to return a bounded typed failure and allow cleanup admission, without waiting for the hung SDK thread. Route the production probing path through the same isolated boundary, with the SDK-in-worker/raw methods separated so the worker does not recursively spawn itself. Full live SDK fault isolation remains the retained joystick architecture; this report only requires closing the pre-configuration probe bypass identified in the original finding.

4. **New registry-read errors skip acquisition rollback for earlier selected IDs.** Inside `acquire_selection`, `ownership_marker(device)?` and `creation_pending_marker(device)?` at `manager.rs:1094-1095` return directly, unlike the surrounding explicit failure branches that call `release_all`. `enable_locked` assumes rollback already happened and simply changes status/returns the error (`:1049-1058`). With selected IDs `[1,7]`, ID 1 can already be acquired and neutralized when reading ID 7's registry marker fails; enable reports failure while ID 1 remains acquired. This is an introduced lifecycle regression on an ordinary registry access error.

   **Targeted regression:** adapter reports both IDs Free and compatible, ID 1 owned, and `ownership_marker(7)` (or pending-marker read) returns `MarkerWriteFailed`. Assert enable returns the error, persisted enabled remains false, and ID 1 has been neutralized/released. Handle these errors through the same rollback path as descriptor/status/acquire failures. This source-proven path was not exercised by the supplied fake, which has no marker-read failure injection.

## Original finding dispositions and evidence

- **Original 1 (consent deadline): fixed at its stated boundary.** `run_bounded` now starts its deadline after successful spawn/consent; the backend supplies an accepted-at timestamp used for confirmation. Cleanup/uncertain outcomes are inspected instead of blindly discarded. The recovery ownership inference remains unsafe as finding 1 above.
- **Original 2 (bounded native status): partial.** The configurator trait now spawns the same executable by its absolute current-exe path, bounds the worker process, parses fixed tokens, and retains incomplete cleanup. `tauri/src-tauri/src/main.rs` dispatches worker mode before Tauri. Production manager preflight still bypasses that boundary (finding 3).
- **Original 3 (tree cleanup/forgetting children): partial.** Failed terminate/reap retains native handles and blocks configuration; `release_runtime` checks settlement. A Job Object covers descendants born after assignment. The startup gap in finding 2 prevents a complete process-tree claim. Windows elevated Job assignment and GUI-subsystem pipe behavior remain native acceptance tests.
- **Original 4 (foreign Compatible): ordinary no-marker path fixed; new pending-marker exception remains unsafe.** Manager enable/retry and cleanup now reject Free devices lacking both markers; configurator rejects unmarked Compatible. ID 1 marker spelling remains interoperable, selected IDs remain 1..16, and fixed arguments never target unrelated IDs.
- **Original 5 (reparse ancestors): fixed.** The anchor is independently derived from current_exe, installed resources must equal anchor/resources, and the probe walks the filesystem root, all anchor ancestors, resource descendants, and the final fixed resource. The original strict-ancestor escape is rejected.

Executed narrowly against the imported actual source: `linked_strict_ancestor_above_anchor_is_untrusted`, `delayed_uac_acceptance_receives_full_post_consent_deadline`, and `process_deadline_terminates_tree_and_reaps_before_returning_timeout` — **3 passed**.
