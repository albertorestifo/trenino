## Actionable findings

1. **P2 — Device-wide conflicting assignments pass configuration validation.** `crates/trenino-core/src/hardware/mod.rs:130` validates each item but never checks cross-item uniqueness. `DeviceConfiguration` with an analog input and button both at pin 1 returns success; two HT16K33 modules at address 112 return success; matrices `{rows:[1], cols:[2]}` and `{rows:[3], cols:[4]}` both return success although both generated virtual-button ranges start at 128. Supervisor compiled a standalone probe against the current core library and observed all three successful results. The legacy `Input.changeset` has a device/pin uniqueness constraint (`lib/trenino/hardware/input.ex:75`); migration `priv/repo/migrations/20251223210242_refactor_matrix_to_separate_entity.exs:210-217` explicitly extends it to virtual buttons. `lib/trenino/hardware/i2c_module.ex` similarly constrains device/address. A successful pure builder must not generate conflicting device identities. Check physical-input pins, module addresses, and generated virtual ranges before emitting the multipart configuration. Preserve the existing virtual-pin formula; do not silently invent offsets for additional matrices. Add rejection tests plus a valid mixed configuration. The adversarial reviewer rated this P1; supervisor rates it P2 for this currently unconnected pure-core slice, while requiring a fix before accepting it as the validated runtime boundary.

2. **P2 — Display alignment changes valid existing output.** `crates/trenino-core/src/hardware/ht16k33.rs:145-150` counts Unicode scalar values and removes dots from the width only for `seven_segment && has_dot`. Legacy `lib/trenino/hardware/ht16k33.ex:303-309` counts graphemes and removes dots whenever `has_dot`, including fourteen-segment displays. Both the legacy Params changeset and UI permit fourteen-segment plus `has_dot=true`. For `encode_string("1.2", 4, false, true, true)`, actual Rust output is `[0,0,6,0,0,64,219,0]`; actual original Elixir output is `[0,0,0,0,6,0,0,64]`. For decomposed `e` + U+0301 + `1` with the same flags, Rust produces `[0,0,251,0,0,0,6,0]`, while Elixir produces `[0,0,0,0,251,0,0,0]`. Thus different digits can move or be truncated. Both reviewers independently found the dot case; the supervisor ran both actual encoders for both cases. Preserve legacy alignment semantics and add differential fixtures for fourteen-segment dots and combining Unicode text. A deliberate correction of the legacy behavior would instead require an explicit compatibility decision.

3. **P2 — Empty matrix axes pass validation and produce configuration packets.** `crates/trenino-core/src/hardware/mod.rs:65-76` checks maximum lengths/product but no minimum, so zero rows or zero columns pass; supervisor's standalone probe confirmed a zero-row/one-column matrix produces successful configuration output. Legacy `Hardware.create_matrix` transactionally creates virtual buttons through `lib/trenino/hardware.ex:527-550`. Its inclusive `0..(count-1)` ranges yield invalid virtual pins and/or duplicates for an empty axis, and `Input.validate_pin_range` rejects virtual pins below 128, so this was not a successfully persisted legacy configuration. Reject either empty axis in the pure validator and test both cases. Actual firmware handling of an empty-axis packet was not tested; no claim of device damage is made.

## Deferred or conditional concerns

- `protocol/codec.rs:416-432` grows its buffer indefinitely until a zero delimiter. This is an inherited resilience risk, not a newly introduced parity regression. The plan explicitly treats bounding/discard-until-delimiter as a behavior change requiring a chosen maximum; no accepted maximum exists in this slice. Before connecting this decoder to a live serial actor, select a cap covering all legal packets and test oversized-frame discard and resynchronization. Do not silently choose a small cap in this fidelity repair.
- The pure Matrix DTO lacks a name/order field and preserves caller-supplied order. Legacy `Hardware.list_matrices` orders by name, and row/column pins by position. The coder explicitly documented this precondition. Require the future persistence-to-DTO adapter to preserve those orders with an integration fixture; the pure builder cannot reconstruct metadata it does not receive.
- Runtime identity/generation scoping, session cancellation/timeouts and terminal detection, calibration collection thresholds/transitions, persistent virtual-button construction, and hardware leases remain deferred. The brief requested pure algorithms, not completion of those runtime behaviors.
- Serial discovery/connection, configuration acknowledgment/persistence, firmware downloads/uploads, and physical-device acceptance were deliberately not judged. No hardware-output corruption or real-port safety claim can be inferred from these pure tests.
