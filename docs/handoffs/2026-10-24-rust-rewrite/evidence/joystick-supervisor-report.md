## Required corrections

1. **P1 — The exact-eight-axis check accepts extra axes.** `vendor/vjoy/src/vjoy.rs:455-465` enumerates only the eight usages 0x30..0x37. Consequently `tauri/virtual_joystick/src/vjoy.rs:206-211` sees eight axes even when the descriptor also contains Wheel, Aileron, Rudder, Throttle, Accelerator, Brake, Clutch, or Steering. The established probe explicitly rejects these usages at `lib/trenino/virtual_joystick/configurator/system_adapter.ex:45-49`. Moreover, `vendor/vjoy/src/vjoy.rs:496,532-539` puts 16384 into extended report fields that the previous adapter zeroed. Reject every supported extra axis and preserve zeroed unused report fields. Fake tests must present each extra usage alongside all eight required axes and verify rejection and no report publication.

2. **P1 — Cleanup relinquishes without neutralizing output.** `tauri/virtual_joystick/src/protocol.rs:174-177,307-309,318-325,340-345` handles Shutdown, update failure, EOF/drop, and I/O exits by relinquishing only. After a held button/nonneutral axis the final submitted report is still active. Pinned SDK `RelinquishVJD` does not itself submit a neutral report; real driver cleanup behavior remains unverified. The plan explicitly requires neutral/reset before orderly release. Attempt a full neutral report before relinquishing, always release exactly once even if neutralization fails, and make explicit shutdown failure observable instead of falsely acknowledging successful neutralization. Test ordered events for nonneutral Shutdown, EOF, input/output failure, direct drop, update failure, and failed neutralization on a non-1 ID. Current tests at `protocol_test.rs:311-320,445-452` assert relinquishment only.

3. **P1 — Missing required DLL exports panic instead of failing load.** `vendor/vjoy/src/vjoy.rs:277-289` accepts `vjoy_sys::vJoyInterface::new` without validating its required function fields. The generated binding stores each lookup as a `Result`; `from_library` returns `Ok` even when symbols are missing, and methods use `.expect("Expected function, got error.")`. Evidence is in `tauri/virtual_joystick/target/debug/build/vjoy-sys-6f171e41f7e517d6/out/bindings.rs:142-306,318-323` and analogous methods. A missing configuration/FFB/update/relinquish export can therefore abort after successful acquisition; release uses `panic = "abort"` (`Cargo.toml:24`), so Drop cannot rescue it. Validate all exports this adapter needs before any SDK operation/acquisition and return a named load error. Add a fake DLL/export-table probe for missing early and late exports; no real SDK/driver is needed.

4. **P2 — Incompatible devices are acquired before validation.** `vendor/vjoy/src/vjoy.rs:445-447` acquires before reading capabilities; `tauri/virtual_joystick/src/vjoy.rs:192-246` validates only afterward. This violates the coding brief's pre-acquisition descriptor requirement and temporarily claims an incompatible selected device. Split the read-only capability query from acquisition, validate first, then recheck as needed for races. Test that incompatible axes/buttons/POV/FFB cause zero AcquireVJD calls, that busy foreign devices are untouched, and that any failure after successful acquisition relinquishes once.

5. **P2 — Failed POV queries become an accepted no-POV descriptor.** `vendor/vjoy/src/vjoy.rs:437,441` clamps signed SDK results with `.max(0)`, erasing negative error results. The pinned API source documents -1/negative as failure for these calls. Preserve failure separately from a zero count; reject uncertain descriptors. The fake capability seam currently returns unsigned counts and cannot express this failure. Change that seam and test independent failures from both POV queries. Also correct the report's claim about failed FFB queries: `has_force_feedback` at lines 158-160 returns `Ok(false)` whenever `IsDeviceFfb` returns false, while the upstream API returns false both for no FFB and for several query failures. Document this native limitation honestly or use a capability probe capable of distinguishing uncertainty; the current `Err` branch does not detect it.

## Further test and integration requirements

- `vendor/vjoy/src/vjoy.rs:231-233` updates the cached `Device` before SDK success. The current sidecar clears/relinquishes the failed session, so it does not replay that cache; nevertheless the public patched crate API does not satisfy the plan's success-only cache contract. Commit the cached state after successful update and add an injected failure/retry test. Preserve the last successful cache on failure.
- Existing vendor tests cover an isolated `fetch_device` helper and slider serialization, not the actual no-acquire constructor, NativeVJoy orchestration, sparse public lookup/update/relinquish APIs, symbol loading, or stdout behavior. Add a fake native function table/DLL seam that exercises the adapter end to end, selected ID 16, sparse ID 9, status changes/acquire races, incompatible descriptors, failed cleanup, and all 32 button bits. Do not run the upstream hardware integration test target.
- Framing is bounded and legacy hello defaults to 1. Add focused checks for output-write/flush errors after acquisition, exact-size/CRLF/invalid-UTF8 inputs, retry after failed initial update, and repeated hello for a selected non-1 device. Future new clients talking to old workers must compare Ready.device with the requested selection; the v1 additive field alone cannot make an old worker honor it.
- Bindgen introduces a **build-time libclang prerequisite** through `vjoy-sys 0.5.2/build.rs`. Local verification used a task-local library; existing CI/nightly/release build steps do not explicitly provision or verify it. Record/provision this prerequisite and demonstrate a clean Windows build; do not claim workflows definitely fail merely because hosted images may already contain LLVM. libclang is not a required end-user runtime DLL.
- Generated bindings currently assert the correct API v3 size (124 bytes), alignment (4), and field offsets, including Slider 40, Dial 44, buttons 76, and final field 120. Slider 1/2 mapping is correct. Retain a pinned ABI/report contract test when changing the SDK dependency.
- DLL selection remains an explicit absolute `vJoyInterface.dll` path. The adapter does not prove that path is a verified installed resource; trusted caller/resource validation remains later integration work. This is not evidence that default path discovery was reintroduced.
