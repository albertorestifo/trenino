# Independent adversarial review: thin Rust-backed UI slice

Reviewed `1942935` and `f7c1c4c` in `codex/rust-rewrite`, limited to `tauri/ui/**` and `crates/trenino-core/src/ui.rs`. This slice is a static shell, read-only presentation, consent UI, generated DTOs and a proposed IPC bridge. The Tauri commands, publisher and full service-backed screens are not implemented here. I did not inspect the supervisor's review notes or modify production sources.

## Findings

1. **P1 — A gap event can be lost permanently during snapshot recovery.** `TopicStream.accept` returns `resync` without retaining the event (`tauri/ui/src/bridge/stream.ts:25`). If the current revision is 4 and revision 6 arrives, then the asynchronous snapshot returns revision 5, `installSnapshot` accepts 5 and revision 6 is gone. The UI remains at 5 until another event arrives; no such event is guaranteed. I reproduced this sequence in a focused Vitest probe. Retain the highest observed event/revision through recovery, or keep fetching until the snapshot reaches it; serialize concurrent refreshes.

2. **P1 — The pre-snapshot event queue is unbounded.** Every event received before the first snapshot is pushed into `buffered` (`tauri/ui/src/bridge/stream.ts:8-13`), including wrong-topic events, with no size or time cap. A burst of 10,000 events produced a 10,000-entry queue in the focused probe. If `ui_get_snapshot` rejects, `refresh` only calls `onUnavailable` (`tauri/ui/src/bridge/client.ts:65-75`), so the queue remains and subsequent events continue accumulating with no retry. Bound/coalesce the queue and provide explicit retry or resubscription recovery after a failed initial fetch.

3. **P1 — Structured Rust errors are collapsed into a fabricated unavailable error.** `command` catches every Tauri rejection and discards its value (`tauri/ui/src/bridge/client.ts:27-34`). A `ui_set_consent` validation/conflict/internal `UiFailure` is therefore shown as retryable `unavailable`, losing the server message and field errors. `subscribe` and `refresh` similarly discard rejection details (`client.ts:59-74`). Decode known `UiFailure` payloads and reserve a generic transport error for unknown failures; validate the error object before displaying it.

4. **P2 — Malformed event revisions can throw out of the event handler.** `accept` passes unvalidated `epoch` and `revision` strings to `BigInt` (`tauri/ui/src/bridge/stream.ts:17-23`). An event with `revision: 'not-a-revision'` throws `SyntaxError`; the listener callback has no catch (`tauri/ui/src/bridge/client.ts:52-56`), so it neither reports unavailability nor resynchronizes. I reproduced the throw in a focused Vitest probe. Validate topic, epoch, revision and payload shape at the IPC boundary and treat malformed events as a recoverable stream fault. Initial snapshots likewise enter `installSnapshot` without runtime validation.

5. **P2 — Old route requests can overwrite the visible route's error state.** `updateRoute` guards only the first settings bootstrap against a changed hash (`tauri/ui/src/app/App.svelte:20-37`). `load` later writes shared `loadError` and page data without checking which route started it (`App.svelte:40-48`). For example, start a configurations request, navigate to Settings and let Settings load, then reject the old configurations request: Settings displays the configurations failure. A route generation/request token should gate each response; consent completion also needs a current-route check before forcing `/` (`App.svelte:50-59`).

6. **P2 — `UiFailure` is labeled safe but does not sanitize its source.** `From<AppError>` copies `error.message` and every `field_errors` value directly (`crates/trenino-core/src/ui.rs:105-120`). Any `AppError` containing a URL with a key, secret, or internal trace can be serialized to the frontend; consumers that receive a `UiFailure` display its message through `load` or consent. The existing redaction test checks only `SettingsView` (`ui.rs:146-160`), not the error path. Either require a demonstrably sanitized `AppError` at the boundary or redact/classify the conversion and test secret-bearing examples.

## Contracts and follow-up gates

- **Epoch ordering is undefined.** `TopicStream` treats a numerically smaller epoch as stale (`stream.ts:17-20,34-37`), while the shared `Epoch` type is a `u64` and the plan only says that restart changes it. If the runtime can restart with a lower epoch, the client ignores the new stream indefinitely. Specify monotonic epoch allocation across restarts or use a restart-safe identity/recovery rule before integration.
- **Same-topic ownership needs definition.** Each `bridge.subscribe` call invokes `ui_subscribe`, and each disposer invokes `ui_unsubscribe` by topic (`client.ts:41-81`). The proposed contract says a window is registered, without a subscriber identity or reference count. With two same-topic consumers, disposing one may remove the other's backend observation. Define per-window reference counting or subscription IDs and test concurrent subscribers and early unmount.
- **Generated declarations are not checked for drift.** The Rust test exports into tracked source files (`crates/trenino-core/src/ui.rs:163-180`) but does not compare generated output with the committed declarations. A stale declaration can pass `npm check/build`, and `cargo test` silently rewrites it. Add a generate-then-diff CI gate, preferably outside the source tree.
- **Live UI consumption remains future work.** `App.svelte` uses `getSettings`, `getConfigurations`, `getTrains` and `setConsent`, but never calls `subscribe`; this is consistent with the declared static/read-only slice, not evidence of live-update parity. The planned integration must exercise stream recovery, route teardown, and subscription ownership before claiming live views.
- **Theme follows the system only at startup.** `tauri/ui/src/main.ts` reads `matchMedia` once and listens for storage/custom events, but not media-query changes. A live OS theme change leaves the UI on the previous palette until reload or another theme event. This is a presentation parity issue, lower priority than the bridge failures.

## Verification performed

Ran a temporary, isolated Vitest probe against `TopicStream`: all three assertions passed, demonstrating the lost revision-6 event after a revision-5 snapshot, a 10,000-entry pre-snapshot buffer, and a `SyntaxError` on malformed revision. The probe file was removed. I did not repeat the already reported broad Svelte/Vitest/build/Rust/audit checks, and left production files unchanged.
