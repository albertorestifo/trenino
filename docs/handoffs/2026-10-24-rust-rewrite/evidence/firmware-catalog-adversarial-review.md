# Firmware catalog adversarial review

Scope: firmware code delivered in `8723455..f79f41e` under `crates/trenino-core/src/firmware` and `crates/trenino-runtime/src/firmware`. I reviewed the supplied firmware brief, implementation report, diff, current firmware source, and relevant legacy source. I did not inspect other reviewers' findings or supervisor notes. Shared-worker repository adapter, app startup/UI wiring, and flashing are separate gates and are excluded from this verdict.

## Findings

1. **P1 — Valid prerelease requirements reject matching firmware.** `crates/trenino-core/src/firmware/compatibility.rs:229-231` returns `false` for every prerelease whenever a requirement is configured, before evaluating its bounds. With installed Elixir 1.20.4, `Version.match?("1.2.3-rc.1", Version.parse_requirement!("== 1.2.3-rc.1"), allow_pre: false)` is `true`; `>= 1.2.3-rc.1` matches `1.2.3-rc.2`, and `< 1.2.3` matches `1.2.3-rc.1`. A standalone Rust harness importing this exact module returned `Ok(false)` for all three, as well as `~> 1.2.3-rc.1` against `1.2.3-rc.1`. This hides compatible releases and blocks selection. **Fix:** implement `Version.match?/3` prerelease behavior for each supported operator and Boolean combination, with an Elixir oracle matrix including explicit prerelease bounds; retain nil accepting every parseable prerelease.

2. **P1 — Cache lookup can return another asset's firmware.** `crates/trenino-runtime/src/firmware/downloads.rs:85-100` names the cache only by release version and environment, while `:110-119` locks by asset row ID and accepts an existing file using only size; `:202-210` does not bind the file to the selected release, asset ID, filename, or URL. Reproduction from the code: construct two valid selections with the same version and environment but different asset IDs/URLs and equal declared sizes; download A, then request B. B returns A's path and bytes without contacting B's server. Concurrent A/B requests also use different locks for the same destination. **Fix:** bind cache entries to a stable release/asset identity (or verified digest if metadata supplies one), lock by final path across requests, and verify that a hit belongs to the selected asset. Keep a deliberate migration path for legacy cache files; file size alone is only a transfer check, not authenticity.

3. **P2 — Existing legacy cache files are invisible offline.** `crates/trenino-runtime/src/firmware/downloads.rs:98-100` produces `1.2.3_uno.hex`; legacy `lib/trenino/firmware/file_path.ex:66-71` produces `v1.2.3_uno.hex`. A valid file already downloaded by the old app therefore misses `valid_cache` and forces a network request, contrary to offline valid cached use and path continuity. **Fix:** recognize and safely validate the legacy `v{version}_{environment}.hex` path, or migrate it atomically to the new asset-bound cache scheme before trying HTTP.

4. **P2 — A syntactically parseable requirement can panic during range expansion.** `crates/trenino-core/src/firmware/compatibility.rs:181-194` adds one to a `u64` major or minor without checking overflow. A standalone harness calling `FirmwareRequirement::parse(Some("~> 18446744073709551615.0"))` panicked at line 183 in debug mode; release mode would wrap. A bad configured policy must fail explicitly. **Fix:** use `checked_add`, return a requirement error when the upper bound cannot be represented, and cover both major and minor overflow.

5. **P2 — Repeated dismissal clears a persisted dismissal.** `crates/trenino-runtime/src/firmware/updates.rs:171-176` derives a key from `notice(devices)`. After the first successful dismissal, `notice` returns `None`; a second `dismiss` persists `None` and clears `dismissed_key`, so the same notice appears again. The same occurs if a dismissal call arrives while no outdated device is connected. **Fix:** make dismissal a no-op when no active notice exists; use a separate explicit reset operation if needed. Test two dismissal calls and disconnect/reconnect across a scheduler restart.

6. **P2 — Redirect policy is checked after the disallowed request.** `crates/trenino-runtime/src/firmware/catalog.rs:244-252` and `crates/trenino-runtime/src/firmware/downloads.rs:129-136` validate only `response.url()` after `send()`. The injected `reqwest::Client` uses its default redirect policy unless callers replace it; the installed reqwest 0.12.28 source documents automatic redirects. An allowed HTTPS manifest/asset URL can respond with a redirect to a non-loopback HTTP or other disallowed target. Reqwest makes that next request before these checks reject its final URL. **Fix:** enforce the URL policy on the initial URL and every redirect before following it, or disable redirects and resolve allowed hops explicitly. Exercise a local fake server returning a redirect to a policy-disallowed target without making any real remote request.

7. **P2 — Dropping the scheduler owner does not stop its timer task.** `crates/trenino-runtime/src/firmware/updates.rs:199-224` stores a `JoinHandle` and cancel sender, but only `cancel(self)` stops the loop; there is no `Drop` behavior. Tokio detaches a task when its `JoinHandle` is dropped, so an owner dropped during shutdown/reconfiguration can leave checks running indefinitely. **Fix:** make the owner abort or signal cancellation on drop, preserve `cancel(self)` for graceful waiting, and test that no checks occur after owner drop.

## Checks performed

- Read the scoped brief, implementation report, supplied firmware diff, all delivered firmware source, and the relevant legacy compatibility, file path, downloader, update checker, device registry, and firmware context source. No correctness report, supervisor checkpoint, or other review findings were read.
- Ran a disposable Elixir oracle script with five requirements and four candidate versions through installed Elixir 1.20.4 / OTP 29. The explicit prerelease cases above returned `true`.
- Compiled a disposable standalone Rust harness against the delivered `compatibility.rs` with `rustc`. It returned `Ok(false)` for four matching prerelease cases and caught the `~>` major overflow panic.
- Ran `git diff --check 8723455..f79f41e` on the two firmware source directories; it passed. I did not rerun the already reported broad test suites or use real GitHub, firmware downloads, user databases, ports, installers, or flashing.

## Verdict

**Spec: fail for this slice. Quality: fail.** The confirmed Elixir compatibility mismatch and cross-asset cache reuse affect firmware selection and the bytes returned for a selected asset. The other findings affect offline continuity, malformed-policy handling, persisted dismissal, URL enforcement, and timer ownership. The repository adapter and UI/startup/flashing gates remain explicitly separate from this verdict.
