# Independent storage migration correctness review

Reviewed commit `63b1a1c` on `codex/rust-rewrite` against the implementation brief, platform plan, both migration-produced fixture schemas/dumps, fixture generation scripts, storage code/tests, the v0.7.4 tag migration list, and the current Ecto migrations. I did not read the supervisor's report or scratch probe before reaching these findings. This is a source review; I did not rerun the already-passing workspace tests or touch an application database.

## Findings

### P1 — Admission is checked before the writer reservation, so a newly unsupported ledger can be migrated

`crates/trenino-runtime/src/storage/migration.rs:147-158` reads `application_id`, `user_version`, the complete schema fingerprint, Ecto version rows, and FK validity **before** `BEGIN IMMEDIATE`. A second connection can commit a ledger-only change after `is_supported_legacy_schema` returns and before line 158 obtains the writer reservation. The backup and transformation then operate on that later database. `validate_full_schema` at lines 275-286 verifies the Rust ledger and FK state but never rechecks the Ecto versions. Thus an extra/newer `schema_migrations` version with no schema change is accepted and preserved instead of refused. This contradicts the exact-version/no-newer-source admission requirement; the writer lock only protects the later snapshot-to-commit interval.

**Required regression:** Coordinate a second connection to insert a future Ecto version after initial admission and before the migration lock (or expose an internal hook to test the boundary). Verify migration refuses it without setting Rust identity/version or creating a misleading backup; also verify a concurrent ordinary data write before lock is either included in a correctly admitted snapshot or handled under an explicit policy. Acquire the reservation before the admission read, or repeat all admission checks under the acquired reservation before backup.

### P2 — A current Ecto train missing its last identifier passes migration unchanged

The current `trains` table and `train_identifiers` FK/index structure permit zero identifiers for a train (`crates/trenino-runtime/src/storage/schema/ecto-current.sql:62-66,171-173`). The legacy application requires at least one in `lib/trenino/train/train.ex:54-79`, and the platform plan explicitly lists a missing last identifier as an acceptance case. `is_supported_legacy_schema` (`migration.rs:252-272`) checks only schema, ledger, and FKs. The current branch of `apply_upgrade` (`migration.rs:342-349`) rebuilds vJoy tables and leaves train rows unchanged, so a train whose final identifier was deleted remains invalid in the Rust full schema. The fixture always inserts one identifier (`tests/fixtures/storage/generate_fixtures.py:24-31`), and no migration test covers this case.

This is a demonstrated gap in admission logic for a schema-valid input, though direct deletion bypasses the legacy changeset. **Required regression:** Create a current migration-produced fixture with a train whose sole `train_identifiers` row is deleted, assert a declared policy (preferably refuse the upgrade without source mutation, since inventing an identifier changes meaning), and cover the same invariant in the later typed train repository so the final identifier cannot be removed through Rust APIs.

### Integration blocker / bounded-slice scope — No fresh full-schema creation or bootstrap-to-full path

`Database::open` creates the three-table version-1 bootstrap when the path is new (`crates/trenino-runtime/src/storage/mod.rs:265-282,313-321`). The only public full-schema constructor is `migrate_legacy`, which accepts exact Ecto sources (`migration.rs:117-125,252-272`) and refuses that bootstrap. Thus a fresh Rust installation currently cannot reach full schema version 2 through the public storage API. The implementation report explicitly limits this slice to retaining the bootstrap; this is **not** a regression in its legacy-copy path, but it blocks the platform plan's fresh-database acceptance and must be tracked before runtime cutover. Add an explicit fresh full-v2 creation path plus a versioned bootstrap-v1 upgrade policy, and test that both open through `SchemaMode::Full` with complete object/ledger validation.

## Verified positive evidence and remaining test gaps

- The tagged `v0.7.4` directory has 36 migrations ending `20260503114723`; current has 41 ending `20260927000000`. `generate.ps1` archives the tag migration directory and the Elixir helper runs those migrations into disposable databases before Python populates deterministic rows and exports `sqlite_master` SQL. Fixture provenance is credible; it does not prove every data shape is exercised.
- The current Ecto schema and `rust-full-v2.sql` differ only by widening both vJoy `device_index` checks from `= 1` to `BETWEEN 1 AND 16`, plus `rust_schema_migrations`. The configuration `id = 1` singleton, mapping target shape, axis/button limits, partial per-device target uniqueness, and input uniqueness remain in the target. The current migration path copies all vJoy columns, including IDs and timestamps, through temporary tables. The existing test verifies index 16 and a duplicate axis conflict; boundary 0/17, second configuration, button exclusivity, and per-device independence should be covered when vJoy repositories are implemented.
- The v0.7.4 identifier transform uses the same SQLite `TRIM`, blank/collision checks, and `CURRENT_TIMESTAMP` insertion pattern as `20260927000000_create_train_identifiers.exs`. Existing train IDs, related IDs, existing timestamps, calibration, script code/triggers, and settings are left in place. The current path leaves I2C module parameters and display bindings in place. Existing tests assert representative values, not exhaustive per-table/column equality.
- Structural admission compares all non-internal SQL-bearing `sqlite_master` objects and exact Ecto version lists. Foreign-key checks happen before and after upgrade; the source remains in one transaction and a separate SQLite Backup API snapshot includes committed WAL data. Tests cover blank/colliding identifiers, rollback, WAL backup, extra schema refusal, and an existing backup. No disposable fault-injection evidence covers disk-full/interrupted backup, and the implementation report correctly does not claim it does.
- The full schema API exposes settings and a compatibility `get_profile` only; mutation methods for profiles are explicitly unsupported on full schema (`mod.rs:202-249`). Full typed domain repositories, changeset validation, and cross-table routing transactions remain later platform work rather than evidence of this migration's correctness.
